## 1. 계획 개요

### 1.1 프로젝트 목표

해양경찰 상황실 업무를 모티브로 하여, 단일 생성형 AI가 질문에 답하는 기존 방식에서 벗어나 **여러 전문 AI가 실제 조직처럼 역할을 분담하고, 상황실장 AI가 이를 지휘·종합·재지시하는 AI 오케스트레이션 기반 상황대응 지원시스템**을 구현한다.

프로젝트의 핵심은 단순히 좋은 답변을 만들어내는 것이 아니다.

**“AI들이 어떻게 조직적으로 움직이는지”를 심사위원이 대시보드에서 직접 관찰할 수 있도록 구현하는 것**이 핵심이다.

최종적으로 다음 흐름을 실시간 시연한다.

```text
신고 / 임무 접수
      ↓
AI 상황실장
      ↓
상황 분석 및 업무 분해
      ↓
┌───────────┬───────────┬───────────┐
↓           ↓           ↓
수색구조 AI   정보분석 AI   자원지원 AI
↓           ↓           ↓
RAG 검색     정보 분석     MCP Tool 호출
└───────────┴───────────┘
      ↓
AI 상황실장 종합
      ↓
Critic AI 교차검증
      ↓
최종 대응방안
      ↓
상황 변경 발생
      ↓
재분석 / 재임무 부여
```

# 2. 교육 및 해커톤 환경 분석

현재 확인된 해양경찰청 교육 커리큘럼은 KISTI 대전 본원에서 진행되는 AI 에이전트 중심 교육이다.

교육에서 다루는 핵심 기술은 다음과 같다.

| 교육요소프로젝트 적용 |                 |
| ----------- | --------------- |
| AI Agent    | 상황실장 및 전문요원 AI  |
| RAG         | 매뉴얼·지침·절차 검색    |
| MCP / Tool  | 외부 정보·가상 시스템 조회 |
| 멀티모델        | 역할별 모델 또는 검증모델  |
| 신뢰성 검증      | Critic Agent    |
| 자연어 처리      | 신고 구조화 및 상황요약   |
| 프로젝트        | AI 상황실 시연       |

특히 이번 프로젝트의 강점은 **교육에서 배운 기술들을 억지로 나열하지 않고 하나의 실제 업무 흐름 속에 자연스럽게 통합할 수 있다는 점**이다.

따라서 발표 메시지는 단순히

> “Agent도 쓰고 RAG도 사용했습니다.”

가 아니라,

> **“이번 교육에서 학습한 Agent, RAG, MCP, 멀티모델 및 신뢰성 검증 기술을 실제 해양경찰 상황실 업무에 통합했습니다.”**

가 되어야 한다.

# 3. 프로젝트 핵심 메시지

프로젝트 전체를 관통하는 메시지는 한 문장으로 압축한다.

> **“기존 AI가 한 명의 유능한 보좌관을 만드는 데 집중했다면, 우리는 하나의 상황실 전체를 AI로 구성했습니다.”**

보조 메시지는 다음과 같다.

> **AI Assistant에서 AI Organization으로.**

그리고 기술적으로는 다음 표현을 사용한다.

> **Hierarchical Multi-Agent Orchestration 기반 AI 상황실**

즉 Hermes나 특정 프레임워크 자체를 앞세우지 않는다.

핵심은 **오케스트레이션 구조 자체**다.

# 7. Hermes 사용 여부

초기 계획에서는 Hermes를 고려했으나 현재 전략에서는 **Hermes를 필수 요소에서 제외한다.**

오케스트레이션 자체는 Python으로 매우 간단하게 구현할 수 있다.

예:

```python
results = await asyncio.gather(
    sar_agent(situation),
    intel_agent(situation),
    resource_agent(situation)
)

decision = await commander(situation, results)

review = await critic(situation, decision)
```

이 정도의 코드만으로도

**병렬 전문 분석 → 종합 → 검증**

구조가 완성된다.

따라서 Hermes는 다음과 같이 판단한다.

```text
Hermes 활용이 매우 쉬움
→ 사용 가능

설정/환경 문제가 발생
→ 즉시 포기

Python + OpenAI API
→ 기본 구현
```

해커톤에서 가장 위험한 상황은 **특정 프레임워크를 살리기 위해 시간을 소비하는 것**이다.

# 8. LLM 및 API 전략

사용자는 현재 OpenAI API를 보유하고 있다.

따라서 기본 전략은 다음과 같다.

```text
Python
 ↓
OpenAI API
 ↓
역할별 Agent
```

모든 Agent가 반드시 최고성능 모델을 사용할 필요는 없다.

예시 구조:

```text
SAR Agent
정보 Agent
자원 Agent
     ↓
빠른 모델

Commander
Critic
     ↓
상위 모델
```

다만 해커톤에서는 복잡한 모델 라우팅보다 **한 모델로 안정적으로 돌아가는 것을 먼저 확보**한다.

그 이후 속도 또는 비용 문제가 있을 경우에만 모델을 분리한다.

# 9. Agent 구성

## 9.1 상황실장 AI — Commander

전체 시스템의 중심이다.

역할:

- 신고 접수
- 사건 분류
- 상황 요약
- 역할별 업무 지시
- 전문 Agent 결과 종합
- 우선순위 결정
- 대응방안 작성
- 상황변화 발생 시 재판단

화면에는 다음과 같이 표시한다.

```text
AI 상황실장

사건 분류
해양사고 / 충돌 / 인명실종

위험도
HIGH

업무지시

→ 수색구조 AI
  실종자 수색 우선순위 검토

→ 정보분석 AI
  사고정보 구조화 및 미확인 정보 확인

→ 자원지원 AI
  필요한 구조자원 검토
```

---

# 10. 수색구조 Agent

담당 역할:

- 인명피해 위험도
- 수색구조 우선순위
- 현장 위험요소
- 필요한 초동조치
- 추가 확인사항

화면 활동 예시:

```text
수색구조 AI
● ACTIVE

현재 작업
수색구조 대응지침 검색

참조자료
✓ 해양사고 대응매뉴얼
✓ 수색구조 절차
✓ 초동조치 체크리스트
```

---

# 11. 정보분석 Agent

담당 역할:

- 신고내용 구조화
- 누락정보 식별
- 사실/추정 분리
- 사건 진행상황 정리
- 상황실장이 판단해야 할 핵심정보 추출

예:

```text
정보분석 AI

확인정보
- 충돌사고
- 승선원 5명

미확인정보
- 사고 발생 정확시각
- 구명조끼 착용 여부
- 선박 침수 상태
```

---

# 12. 자원지원 Agent

담당 역할:

- 필요 구조자원 판단
- 가용자원 확인
- 현장 지원방안 검토
- 추가 지원세력 검토

MCP 또는 Tool 활용을 가장 자연스럽게 보여줄 수 있는 Agent다.

가상의 MCP 결과 예:

```text
가용 구조세력 조회

P-123
✓ 출동 가능

P-456
× 임무 수행 중

구조대 A
✓ 대기 가능
```

# 13. Critic Agent

AI의 신뢰성을 높이는 역할이다.

검증 범위는 네 가지만 유지한다.

```text
1. 근거 없는 판단
2. 누락된 중요정보
3. 상충되는 조치
4. 사실과 추정 혼동
```

결과 예:

```text
CROSS CHECK

⚠ 구명조끼 착용 여부 미확인
⚠ 실제 가용세력 확인 필요
✓ 조치 우선순위 간 충돌 없음
✓ 매뉴얼 근거 확인
```

여기서 교육과정의 **AI 신뢰성 검증** 요소를 직접 보여준다.

---

# 14. RAG 활용 전략

RAG를 거대한 시스템으로 만들 필요는 없다.

해커톤에서는 소규모 자료 몇 개만 있어도 충분하다.

예:

```text
해양사고 초기대응 지침
수색구조 기본 절차
상황보고 기본절차
장비/자원지원 절차
```

수색구조 Agent가 판단할 때 화면에서:

```text
RAG SEARCH

검색 중...

✓ 관련 문서 3건 발견

근거:
[수색구조 지침]
인명피해 발생 시 인명구조를 우선하여...
```

와 같은 형태로 보여준다.

**RAG의 존재가 아니라 RAG가 실제 판단에 사용된다는 것을 보여주는 게 중요하다.**

---

# 15. MCP 활용 전략

MCP는 과도하게 복잡하게 구현하지 않는다.

한 개의 Tool만 정상 작동해도 충분하다.

가장 추천하는 것은:

**가용 구조자원 조회**

다른 후보:

- 기상정보 조회
- 선박정보 조회
- 상황보고 템플릿 조회

예:

```text
자원지원 AI
↓
MCP TOOL CALL
↓
get_available_units()
↓
경비함정/구조대 결과 반환
```

이것 하나만 제대로 보여도 발표에서

> “Agent가 답변만 생성하는 것이 아니라 MCP를 통해 외부 도구를 직접 사용합니다.”

라고 설명할 수 있다.

# 16. 핵심 차별화 — 상황 변화와 재오케스트레이션

이 기능은 반드시 구현을 시도한다.

최초 신고:

```text
21:14
동해항 동방 8해리
어선 충돌
승선원 5명
실종자 1명
```

최초 AI 대응 후 추가 상황을 입력한다.

```text
21:27
실종자 3명으로 변경
파고 3m
선체 침수 진행
```

그러면 대시보드가 다음처럼 변한다.

```text
⚠ SITUATION UPDATED

주요 변경사항
실종자 +2
기상 악화
침수 진행

기존 대응계획 재검토
```

이후 Agent 카드가:

```text
✓ 완료
```

에서

```text
● 재분석 중
```

으로 변경된다.

그리고 상황실장이 새로운 임무를 부여한다.

이 기능이 들어가면 프로젝트가 단순한 **AI 분석 시스템**이 아니라 실제 **상황대응 오케스트레이션 시스템**으로 보이기 시작한다.

# 18. AI의 '생각'을 어떻게 보여줄 것인가

AI 내부의 원문 추론을 그대로 보여주는 방식은 사용하지 않는다.

대신 다음 세 가지를 보여준다.

```text
현재 수행 작업
판단 요약
사용한 도구/근거
```

예:

```text
수색구조 AI

현재 작업
실종자 발생에 따른 수색 우선순위 검토

판단 요약
인명피해 가능성이 가장 높아
구조조치를 최우선 검토합니다.

참조
수색구조 매뉴얼 3건
```

# 51. 최종 한 줄 피치

그리고 기술적 한 줄은:

> **“Agent, RAG, MCP, 멀티모델 검증을 하나의 실시간 AI 오케스트레이션 시스템으로 통합했습니다.”**

## 최종 방향

지금까지의 논의를 종합하면 **Hermes 자체를 잘 쓰는 대회가 아니라, KISTI에서 배운 AI 기술을 이용해 얼마나 설득력 있는 실제 업무형 시스템을 만들어내느냐가 핵심**이라고 보는 것이 맞다.

따라서 프로젝트의 우선순위는

**기술 개수 → 구현량 → 코드 난도**

순이 아니라,

**문제의 명확성 → 오케스트레이션의 가시성 → 실제 동작 → 교육기술 활용 → 시연 완성도**

순으로 잡는 것이 좋다.

그리고 이 계획에서 가장 투자할 부분은 **최종 답변의 정확도보다 “AI 상황실이 실제로 움직이고 있다는 것을 보여주는 Dashboard UX”**다. 그게 완성되면 3\~5분짜리 짧은 발표에서도 프로젝트의 개념과 기술 수준을 상당히 빠르게 전달할 수 있다.
