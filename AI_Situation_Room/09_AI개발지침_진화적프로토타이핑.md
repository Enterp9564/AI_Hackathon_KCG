## 1. 최우선 개발 원칙

**심사위원에게 증명할 가치와 교육성과를 먼저 정하고, 그 증거를 보여주는 작은 사용자 흐름부터 설계·구현·실행한다.**

이 프로젝트는 짧은 시간 안에 시연까지 완료해야 하는 교육형 해커톤이다. 사용자의 최우선 목표는 수상 경쟁력을 갖춘 결과물을 준비하는 것이다. 심사 취지에 맞는 문제 선택, 배운 기술의 종합적 적용, 명확한 시연과 설명을 함께 설계한다.

작동하는 기능은 필요조건이다. 그 기능이 어떤 업무문제를 해결하고 어떤 교육내용을 적용했는지가 화면과 발표에서 드러나야 한다. 수상 가능성이나 점수를 근거 없이 보장하지 않는다.

AI는 처음부터 전체 시스템의 완벽한 아키텍처나 방대한 구현계획을 완성하려 하지 않는다. 동시에 아무 구조 없이 코드를 늘리지도 않는다. 제품 목표와 최소 데이터 계약을 유지하면서, 실제 동작을 확인할 수 있는 작은 단위로 전진한다.

개발의 기본 반복은 다음과 같다.

1. 다음 시연 장면에서 증명할 업무 가치와 교육요소를 선택한다.
2. 필요한 변경, 성공 기준, 심사위원에게 보여줄 증거를 짧게 정리한다.
3. 입력부터 결과까지 이어지는 최소 기능을 구현한다.
4. 실제 실행으로 확인한다.
5. 결과를 사용자에게 보여주고, 발견한 문제를 다음 작업에 반영한다.

기존에 승인된 구현 범위 안의 다음 작업은 매번 허락을 다시 묻지 않고 진행한다. 사용자가 검토만 요청했다면 구현이나 외부 변경까지 확장하지 않는다. 필요한 권한·접근 통제는 이 지침으로 생략할 수 없다.

## 2. 제품 방향의 기준

AI 종합상황실은 사용자가 상황실장과 채팅하며 사건 정보와 첨부자료를 제공하고, 상황실장이 요원에게 지시해 조사·보고·검증을 수행하며, 현재 상황과 대응계획을 갱신하는 시스템이다.

다음 방향을 유지한다.

- 최신 사용자 결정: 상황실장 포함 전 역할 GPT-6 Luna medium. 화면에서 모델명·추론 수준을 숨긴다. 세션별 기억 격리와 가정 기반 시뮬레이션 조언은 12번 문서를 따른다.
- 세션 소유 데이터·임무·검색·캐시에 session_id를 전달한다. 전역 대화 이력·마지막 응답 ID를 여러 세션에서 공유하지 않는다.
- 사용자의 주된 소통 창구는 상황실장 채팅창이다.
- 요원은 정보요원, 수색구조요원, 자원지원요원, 검증요원으로 구성한다.
- 상황실장은 필요한 요원을 선택하고 자연어 임무를 부여한다.
- 프로그램은 임무 전달, 실행, 상태 기록, 저장을 담당한다.
- 대시보드는 실제 지시·보고 대화와 업무 진행을 보여준다.
- 현재 상황과 대응계획은 새 정보에 따라 바뀌고 이전 기록은 남는다.
- 역할 명칭은 범용적으로 두고 해양사고를 첫 시연 사례로 사용한다.

이 지침은 ‘어떻게 개발할 것인가’를 다룬다. 제품 범위는 `01_프로젝트.md`, 구현 순서와 상태는 `04_개발계획.md`, 설계 이유는 `08_AI종합상황실_설계구상서.md`를 함께 참고한다. 자료가 충돌하면 사용자의 최신 명시적 결정을 확인하고, 공식 사실·사용자 선호·AI의 추정을 분리해서 기록한다.

### 2.1 시상 취지 분석을 개발의 출발점으로 삼는다

먼저 제공받은 커리큘럼, 대회 안내, 사용자의 현장 정보를 함께 읽는다. 특정 문장만 근거로 전체 방향을 결정하지 않는다.

다음 세 층으로 정리한다.

| 구분 | 기록할 내용 | 취급 원칙 |
|---|---|---|
| 공식 확인 | 교육 주제, 일정, 공개된 심사기준·배점, 제출 조건 | 근거 자료에 따라 반영 |
| 사용자 제공 | 참가 규모, 실제 운영 안내, 목표와 우선순위 | 공식 자료와 충돌하면 불일치를 표시 |
| 전략적 해석 | 업무 적용, 교육 통합, 완성도 등이 중요할 것이라는 판단 | 가정으로 표시하고 실제 배점처럼 쓰지 않음 |

현재의 전략적 해석은 ‘배운 AI 기술을 이해하고 실제 업무문제에 종합적으로 적용한 결과를 보여주는 것’이다. 제공 커리큘럼에는 우수 프로젝트 시상과 과학기술정보통신부장관상이 명시돼 있다. 공식 배점표는 확인되지 않았으므로 임의 점수표를 실제 수상 기준처럼 사용하지 않는다.

발표는 공식 자료의 팀별 10분 표기를 기록하고, 5분 압축본을 함께 준비한다. 참가 약 20팀과 전체 발표 120분의 불일치는 확인할 사항이다. 팀 전환이나 질의응답이 포함되는지는 추정으로 확정하지 않는다.

### 2.2 교육내용을 기능·증거·발표에 연결한다

Agent, RAG, MCP 기반 도구 연동, 멀티모델 비교, 신뢰성 검증은 교육 통합의 핵심 항목으로 계획에 포함한다. 하나의 시나리오 안에서 각 기술이 필요한 이유와 실제 증거가 연결되게 한다.

| 교육 내용 | 구현 또는 검증 방식 | 심사위원에게 보여줄 증거 |
|---|---|---|
| 자연어 처리·언어모델 | 신고·대화에서 사건과 임무 생성 | 원문과 구조화된 상황·지시의 연결 |
| 텍스트 처리·임베딩 등 | 문서 분할과 검색 방식의 이해를 자료 검색에 반영 | 필요한 경우 검색 단위와 결과 설명 |
| AI 에이전트 | 상황실장의 지시, 요원의 수행·보고 | 실제 수신자·지시문·결과가 연결된 대화 |
| RAG | 조회한 지침·자료를 답변의 근거로 사용 | 검색된 부분과 그것을 반영한 조치 |
| MCP 기반 도구 연동 | 기상 조회 도구 1개를 실제 MCP로 연결 | 실제 호출·반환값·대응안 반영 |
| 멀티모델 비교 | 같은 입력과 기준으로 두 모델의 결과 비교 | 모델명, 조건, 누락·근거·응답시간 비교표 |
| 에이전트 신뢰성 검증 | 모순·누락 사례, 규칙 검사, 검증요원 점검 | 발견한 오류와 대응안의 수정 또는 확인 요청 |

교육에서 소개한 모든 알고리즘을 별도 기능으로 만들 필요는 없다. CNN이나 Word2Vec처럼 기초 교육 내용은 역할을 설명할 수 있게 이해하고, 현재 문제에 필요하지 않은 재학습 기능을 억지로 넣지 않는다. 종합적 수용은 기술 이름의 나열이 아니라 업무 흐름과 설계 판단에 대한 이해를 뜻한다.

멀티모델 비교는 사전 동일 조건 실험으로 준비할 수 있다. 매 시연마다 모든 모델을 동시에 호출할 필요는 없다. 비교 결과를 실제로 측정하기 전에는 우수성·속도 수치를 쓰지 않는다.

RAG는 벡터 검색에만 한정하지 않는다. 키워드 검색으로 찾은 관련 자료를 생성 입력에 넣고 답변에 활용해도 검색 증강 구조로 설명할 수 있다. 고정 문구나 문서 이름만 보여주면서 실제 검색을 했다고 표현하지 않는다.

MCP를 시간 때문에 로컬 Tool로 대체하면 도구 연계는 보여줄 수 있지만 MCP 적용을 증명한 것은 아니다. 교육 플랫폼의 예제를 활용해 최소 MCP 연결을 먼저 검토한다. 핵심 교육요소를 구현하지 못하면 미달 항목과 대안을 명시하고 사용자의 판단을 받는다.

### 2.3 무엇을 먼저 보여줄지 정한 뒤 개발한다

발표는 긴 조직도·기술 소개보다 ‘사용자가 정보를 주자 AI 조직이 어떻게 움직이는가’를 먼저 보여준다. 아래 순서를 기본 시연으로 삼는다.

| 순서 | 보여줄 장면 | 전달할 의미 |
|---|---|---|
| 1 | 짧은 사건 제시 후 상황실장 채팅에 입력 | 실제 업무문제와 사용자 참여 |
| 2 | 상황실장이 요원에게 지시하고 실제 보고가 돌아옴 | 역할 분담과 지휘 구조 |
| 3 | 검색 근거·실제 기상·등록 세력 조회가 대응안에 반영됨 | 교육기술이 답변에 실제 기여 |
| 4 | 명부·새 정보를 제공하자 모순 확인과 재지시가 발생 | 변화에 대응하는 차별점 |
| 5 | 검증 결과, 변경된 상황판·대응계획·이력 표시 | 신뢰성과 업무 완결성 |
| 6 | 교육요소 대응표와 모델 비교 결과를 짧게 설명 | 배운 내용의 종합적 적용 |

첫 1분 안에 핵심 작동 장면으로 진입하는 것을 리허설 목표로 한다. 마지막까지 기능 소개만 하다가 실제 시연을 급히 끝내지 않는다. 발표시간이 줄어도 추가 정보 반영과 재지시 장면을 유지한다.

### 2.4 기능 우선순위는 시연 증거로 정한다

새 작업을 선택할 때 아래를 순서대로 판단한다.

1. 전체 시연의 연결을 막는 문제인가?
2. 핵심 교육요소의 실제 적용을 증명하는가?
3. 사용자 정보 제공 → 지휘 → 조사·보고 → 계획 갱신의 차별점을 강화하는가?
4. 심사위원이 화면에서 쉽게 이해할 수 있는가?
5. 남은 시간 안에 구현과 검증을 끝낼 수 있는가?

미세한 애니메이션, 새로운 Agent, 추가 파일 형식보다 아직 비어 있는 핵심 교육 증거를 우선한다. 기술을 연결하는 작업과 그 결과를 알아보기 쉽게 보여주는 작업을 함께 완료한다.


### 2.5 최신 API·자료·저장 범위를 지킨다

- 외부 데이터 API는 무료 기상·해상 조회만 구현한다. 선박·MMSI·AIS는 초기 범위에서 제외한다.
- 무료 합의는 외부 데이터에 관한 것이다. LLM API의 비용·한도는 별도로 확인한다.
- 정보요원이 기상을 조회하고, 일반기상·해양 호출을 도구 하나로 묶는다. 예측값을 실측으로 표시하지 않는다.
- 기상은 기준시각·조회시각·좌표·단위·출처를 저장한다. 시연을 위해 파고 상승을 만들어내지 않는다.
- 사건·대화·임무·명부·기상·계획은 일반 DB에, 지침 구절은 벡터DB에 둔다.
- Chroma 로컬 영속 저장과 한국어 로컬 임베딩을 기본 후보로 검증한다. 교육 플랫폼 검색 재사용도 검토한다.
- 명부는 전체 데이터를 ID로 대조한다. top-k 검색으로 인원수를 세지 않는다.
- 동해 세력 목록은 사용자 제공 운영자료를 로컬 카탈로그로 등록한다. 실제 위치·가동 상태·출동 완료는 별도 확인이며 가상 시나리오와 구분한다.
- 시연 입력과 정정 수치는 02를 따른다. 불일치가 있으면 확인 질문을 먼저 한다.
- API 검증 사실과 후보의 미검증 상태는 10을 참조한다.

## 3. 첫 구현 전에 정할 최소 사항

초기 설계는 짧은 메모 수준으로 제한한다. 아래 기준이 정해지면 첫 구현에 착수할 수 있다.

| 항목 | 필요한 결정 |
|---|---|
| 평가 취지 | 공식 교육목적·심사기준과 우리 가정을 구분했는가 |
| 첫 사용자 흐름 | 사용자가 무엇을 입력하고 심사위원이 어떤 가치를 확인하는가 |
| 실행 경로 | 현재 사용할 수 있는 UI와 AI 호출 방법 |
| 최소 데이터 | 사건 ID, 메시지, 임무, 보고, 상황 버전의 연결 방식 |
| 책임 경계 | AI는 지시·보고·갱신안 생성, 프로그램은 실행·검증·저장 |
| 성공 기준 | 어떤 입력으로 어떤 결과가 보이면 이번 단계가 완료인가 |

실행을 막는 플랫폼 기능은 추측하지 않고 작은 연결 실험으로 확인한다. 연결 가능성이 미확인인 플랫폼 위에 전체 설계를 고정하지 않는다.

멀티테넌시, 범용 플러그인 시스템, 대규모 분산 처리처럼 현재 시연에 필요하지 않은 설계를 먼저 만들지 않는다.

## 4. 매 반복의 작업 규칙

### 4.1 시작 메모

구현 전 아래 내용을 5줄 안팎으로 알린다. 긴 계획서를 매번 새로 쓰지 않는다.

```text
이번 목표: 사용자 입력으로 상황실장이 정보요원에게 지시하고 보고받는다.
교육·시연 증거: 자연어에서 생성된 임무와 실제 요원 보고를 화살표 선택으로 보여준다.
최소 변경: 임무 형식, 정보요원 호출 함수, 대화 이벤트 표시.
성공 기준: 신고 1건으로 지시와 보고가 같은 임무 ID에 연결되어 보인다.
이번 제외: 다른 요원 추가, 도면 OCR, 복잡한 애니메이션.
검증: 가상 선박 신고 1건과 조회 실패 1건을 실행한다.
```

### 4.2 구현

- 한 번에 핵심 사용자 흐름 하나를 완성한다.
- UI 전체, DB 전체, Agent 전체를 따로 완성한 뒤 마지막에 통합하지 않는다.
- 기존에 작동하는 흐름 위에 다음 기능을 더한다.
- 전체 미래 단계를 한꺼번에 구현하지 않는다.
- 코드를 생성한 것으로 끝내지 말고 실행 방법까지 연결한다.

### 4.3 확인과 보고

각 반복은 다음 내용을 남긴다.

- 이번에 실제로 동작하는 것
- 이 기능으로 증명할 교육내용과 시연 장면
- 실행한 확인 방법과 결과
- 아직 모의 처리이거나 미검증인 부분
- 다음에 확인할 가장 중요한 한 가지

전체 작업을 승인받았다면 짧게 진행 상황을 공유하고 다음 단계로 이어간다. 선택이 제품의 방향을 크게 바꾸거나 새로운 권한이 필요한 경우에만 멈춰 질문한다.

### 4.4 작업시간 관리

초기 운영값으로 한 반복을 약 15분에서 30분 규모로 나눈다. 이는 성능 보장이나 강제 종료 시각이 아니라 작업을 작게 유지하기 위한 기준이다.

하나의 문제에 약 10분 동안 진전이 없으면 원인, 시도한 것, 다음 가설을 정리한다. 같은 수정을 반복하지 말고 최소 재현 또는 더 단순한 경로로 전환한다. 검증시간을 없애서 일정을 맞추지 않는다.

## 5. 프로젝트 구현 순서

아래 순서는 기본 경로다. 실제 연결 실험에서 발견한 의존성에 따라 순서를 바꿀 수 있으며, 변경 이유를 짧게 남긴다.

| 단계 | 작동시킬 최소 흐름 | 완료 증거 |
|---|---|---|
| P0 연결 확인 | 채팅 입력 → 상황실장 실제 응답 | 같은 화면에서 입력과 응답 확인 |
| P1 지시·보고 | 상황실장 → 정보요원 → 상황실장, 추가 메시지로 1회 재지시 | 임무 ID로 연결된 실제 지시문·보고문과 변화 |
| P2 기상 | 사건 위치 → 실제 기상 도구 → 정보요원 보고 | 값·단위·시각·출처・실패 표시 |
| P3 자료 반영 | CSV 명부 대조 → 불일치 질문 → 사용자 정정·저장 | S0/S1/S2 집계와 이전 기록 |
| P4 전문업무 | 벡터 검색·수색구조·자원지원 | 근거 인용과 등록 세력 카탈로그 반영 |
| P5 MCP·검증 | 실제 MCP 기상 경로와 검증요원 연결 | 프로토콜 요청·응답과 오류 검출 |
| P6 소통·복원 | 화살표·상황판·계획 변경·복원 | 실제 이벤트와 화면·이력 일치 |
| P7 시연 정리 | 모델 비교·장애 처리·리허설 | 실제 비교표와 정상·실패 실행 |

P1에서 추가 메시지로 재지시하는 가장 작은 흐름까지 확인해 핵심 차별점을 후반에 처음 시도하지 않는다. 채팅·기본 상태 표시와 저장은 P0부터 붙이며 P6까지 미루지 않는다. P2에서 P4까지 기상·자료·근거를 연결한다. 처음부터 모든 요원과 모든 파일 형식을 구현하지 않는다.

모델 비교용 사례와 검증 정답은 초기 데이터 준비 때 함께 만든다. 실제 연결과 결과 기록은 관련 호출이 작동하는 즉시 진행한다. 전체 작업시간의 첫 절반 안에 작은 전체 흐름이 돌아가게 하는 것을 목표로 하며, 실패하면 기능 폭을 줄여 연결부터 완성한다.

문서 검색은 수색구조요원, 실제 기상 조회는 정보요원, 로컬 등록 세력 조회는 자원지원요원에 연결한다. 구현 단계의 단일 기준은 04이며 변경 시 두 문서의 P0부터 P7 표를 함께 맞춘다. 어떤 검색·도구가 실제로 구현됐는지 표시한다.

## 6. 데이터 계약은 작게 시작하되 명확히 한다

처음에는 다음 정보가 연결되면 된다. 아래는 논리적 필드 예시이며 별도 테이블이나 클래스를 모두 만들라는 요구가 아니다.

| 대상 | 최소 정보 |
|---|---|
| 사건 | 사건 ID, 현재 상황 버전, 요약, 확인 필요사항 |
| 메시지·이벤트 | ID, 사건 ID, 송신자, 수신자, 종류, 내용, 기록시각 |
| 임무 | 임무 ID, 담당 요원, 지시문, 기준 상황 버전, 상태 |
| 보고 | 임무 ID, 결과 요약, 근거, 불확실성, 기준 상황 버전 |
| 첨부자료 | 자료 ID, 사건 ID, 원본 위치, 분석 상태, 추출 결과 |
| 대응계획 | 계획 버전, 기준 상황 버전, 조치, 변경 이유, 검증 상태 |

미래를 예상해 필드를 대량으로 추가하지 않는다. 구조를 바꿀 때는 데이터를 만드는 곳과 읽는 곳을 함께 수정하고 기존 핵심 흐름이 유지되는지 확인한다.

## 7. 설계 변경과 리팩터링 규칙

설계는 초기 문서가 아니라 실행에서 확인한 필요에 따라 발전시킨다.

다음 상황이면 작은 리팩터링을 한다.

- 같은 처리가 반복되어 다음 기능 연결에 실제 오류를 만든다.
- UI와 AI 호출이 섞여 상태 갱신을 수정하기 어렵다.
- 사건 버전과 보고 연결이 불명확해 잘못된 결과가 반영된다.
- 현재 구조가 바로 다음 사용자 흐름을 구현하는 데 장애가 된다.

그 외에는 작동하는 코드를 새 프레임워크로 통째로 다시 작성하지 않는다. 파일 수와 계층 수는 구현 중 실제로 필요해질 때 늘린다.

완료된 동작을 보존한 상태에서 작은 변경을 적용한다. 기술 스택 전체 교체가 필요하면 해결하려는 문제, 대안, 기존 동작 보존 방법을 사용자에게 설명한다.

## 8. 모의 실행과 실제 기능을 구분한다

모의 데이터는 UI 연결과 실패 재현을 빠르게 확인하는 수단으로 사용한다.

- 모의 응답·저장된 실행 재생에는 그 상태를 표시한다.
- 실제 AI 연결을 후반까지 미루지 않는다. 가장 먼저 호출 위험을 확인한다.
- 모의 구현과 실제 구현은 가능한 한 같은 입력·출력 형식을 사용한다.
- 순차 실행을 동시에 움직이는 화면으로 바꿔 병렬 처리라고 설명하지 않는다.
- 도구를 호출하지 않았는데 검색·조회 완료 로그를 만들지 않는다.
- 로컬 함수 호출은 로컬 Tool로 표시하고 실제 MCP 연결과 구분한다.
- 조회 실패를 예시 값으로 조용히 대체하지 않는다. 실패 또는 재생 모드 전환을 알린다.

완료 상태는 실제 처리 결과에 연결한다. 애니메이션은 이 결과를 이해하기 쉽게 표현하는 용도로만 사용한다.

## 9. 상황실장과 요원의 실행 규칙

- 상황실장은 필요한 요원과 임무를 선택한다.
- 허용된 요원 목록과 지시 형식은 프로그램이 검사한다.
- 독립된 임무만 병렬로 실행한다. 다른 요원의 결과에 의존하는 임무는 기다린다.
- 요원은 결과·근거·확인 필요사항을 구분해 보고한다.
- 현재 사건과 무관한 전체 대화나 모든 자료를 매 호출에 전달하지 않는다.
- 공통 상황 요약, 해당 임무, 필요한 자료를 중심으로 문맥을 구성한다.
- 할 일이 없으면 대기한다. 요원끼리 계속 대화하도록 루프를 만들지 않는다.
- 초기에는 보완 지시 최대 1회, 호출별 시간제한과 제한된 재시도를 명시적으로 둔다. 실측 후 설정을 조정한다.

새 정보가 처리 중 들어오면 먼저 접수·저장한다. 실행 중 보고가 이전 상황을 기준으로 했다는 정보를 유지하고, 최신 상황을 자동으로 덮어쓰지 않게 한다.

## 10. 기록과 자료의 정확성

빠른 구현에서도 다음 사항은 유지한다.

1. 신고·자료 원본과 이전 대응안을 보존한다.
2. 신고자 진술, 문서 기재, 조회 결과, AI 추정을 구분한다.
3. 새 정보와 기존 정보가 충돌하면 불일치 상태로 표시한다.
4. AI는 상황 갱신안을 만들고 프로그램은 버전·형식을 검사해 저장한다.
5. 같은 이벤트가 다시 처리돼도 상황일지와 인원 수가 중복 반영되지 않게 한다.
6. 지원하지 않는 파일은 지원하지 않는다고 표시한다.
7. 가상 명부와 자료로 시연하고, API 키를 소스·화면·로그에 노출하지 않는다.

검증요원 도입 전에라도 인원 합계와 필수 항목 같은 명확한 규칙은 프로그램으로 점검한다. 검증요원이 있다고 모든 결과가 정확하다고 설명하지 않는다.

## 11. 최소 검증과 완료 기준

각 단계에서 그 단계의 성공 기준을 실제로 실행해 확인한다. 단순 표시 변경에 과도한 테스트를 만들지는 않되, 상태·자료·호출 경계는 중요한 오류를 확인한다.

| 변경한 기능 | 필요한 확인 |
|---|---|
| 채팅 | 입력과 응답 연결, 실패 시 오류 상태 표시 |
| 임무 전달 | 담당 요원과 보고의 임무 ID 일치 |
| 병렬 처리 | 독립 작업의 실행 구간이 실제로 중첩됨 |
| 자료 분석 | 가상 명부의 정답과 추출 결과 대조 |
| 상황 갱신 | 모순·정정 반영, 이전 버전 보존 |
| 저장 | 재실행 후 사건과 대화·계획 복원 |
| 재오케스트레이션 | 새 정보가 지시와 결과에 실제 반영됨 |
| 실패 처리 | 요원·도구 한 개 실패를 정상 성공으로 표시하지 않음 |

완료는 ‘코드를 작성함’이 아니라 ‘입력부터 기대한 결과까지 실행으로 확인함’을 뜻한다. 실행 환경이나 자격증명이 없어 확인할 수 없으면 구현 완료와 검증 미완료를 구분해 보고한다.

응답시간은 실제 측정값으로 기록한다. 측정 전의 15초·20초 같은 수치를 달성한 성능처럼 말하지 않는다.

## 12. 시간 부족과 장애 시 우선순위

### 12.1 시연·제출 시간을 먼저 확보한다

실제 개발 가능한 시간과 발표 준비시간을 구분한다. 커리큘럼상 명시된 프로젝트 수행은 2시간이며, 다음 날 발표 준비 2시간 30분 전체를 개발시간으로 자동 합산하지 않는다. 코드 수정 금지라고 단정하는 것도 피하고 현장 안내를 확인한다.

개발 시작 때 전체 가용시간의 마지막 약 20%를 통합 확인과 백업에 남기는 것을 초기 계획값으로 삼는다. 별도로 발표자료 제출시각에서 역산해 시연 녹화·실행 점검·리허설 시간을 확보한다. 모든 기능이 끝난 뒤 남는 시간에 발표를 준비하는 방식은 사용하지 않는다.

제공 예제, 사전 검증된 부품, 사용 가능한 계정·도구가 없는 상태라면 전체 범위의 2시간 완성을 약속하지 않는다. 실제 제약을 확인하고 필요한 준비를 먼저 수행한다.

### 12.2 단계별 제출 가능한 결과를 유지한다

각 반복이 끝날 때 해당 장면의 실행 결과, 한 문장 설명, 화면 캡처 또는 기록을 남긴다. 성공한 전체 시연은 재생용으로 보관하고, 이후 변경이 실패하더라도 마지막 정상 버전으로 발표할 수 있게 한다. 재생 영상은 실시간 실행으로 소개하지 않는다.

### 12.3 축소 판단

문제가 발생하면 먼저 현재 작동하는 흐름을 보존한다.

축소 순서의 기본값은 다음과 같다.

1. 장식적 애니메이션과 화면 세부 효과를 줄인다.
2. 첨부자료 형식을 시연에 쓰는 한 가지로 줄인다.
3. 선택적인 기상 항목과 부가 도구를 줄인다. 기상 장애는 미확인 상태로 두고, 재생 자료는 별도 재생 모드로만 사용한다.
4. 보완 지시와 선택 기능을 줄인다.
5. 여전히 전체 흐름이 불가능하면 요원 수나 필수 기능의 축소안을 설명한다.

상황실장 채팅, 실제 지시·보고, 정보의 출처와 변경 기록은 핵심 흐름으로 유지한다. 중요한 제품 범위 축소를 조용히 결정하지 않는다.

시연 백업은 복구 수단이며 실제 구현을 대신한 완료 증거로 사용하지 않는다.

## 13. 문서·체크포인트 운영

- 현재 반복의 짧은 작업 메모와 완료 증거를 남긴다.
- 실행 방법과 필요한 설정을 README에 유지한다.
- 기존 개발계획의 진행 기록 영역 등 한 곳에 완료·미완료·다음 작업을 정리한다.
- 큰 기술 선택이 바뀌면 이유를 짧게 기록한다. 모든 변경마다 새 문서를 만들지 않는다.
- Git을 사용하는 환경이라면 실행 가능한 지점마다 관련 변경만 체크포인트로 남긴다. 사용자의 기존 수정과 비밀정보를 섞어 넣지 않는다.
- 다른 AI가 이어받을 수 있도록 현재 실행 상태와 남은 문제를 구체적으로 남긴다.

현재 문서는 프로토타이핑 방법을 정하는 지침이다. 구현을 시작하면 실제 작동 상태에 맞춰 제품 문서와 개발계획도 필요한 부분만 갱신한다.

## 14. 피해야 할 AI 개발 행동

- 전체 아키텍처 설계와 문서 작성만 반복하며 첫 실행을 미루는 것
- 첫 프로토타입부터 모든 요원·자료 형식·복구 기능을 동시에 만드는 것
- 지금 사용하지 않는 추상화·프레임워크·DB 구조를 만드는 것
- 작은 변경을 이유로 전체 프로젝트를 재생성하는 것
- 공통 형식을 맞추지 않고 여러 파일에 서로 다른 스키마를 만드는 것
- 실제 기능 없이 그럴듯한 상태·검색 로그만 표시하는 것
- 실행하지 않은 코드를 완료했다고 말하는 것
- 이미 해결한 검사를 근거 없이 반복해 시간을 사용하는 것
- 발표시간·교육 플랫폼·팀 규모 등 불확실한 정보를 사실로 고정하는 것

## 15. 코딩 AI에게 전달할 핵심 지시문

> 이 프로젝트의 최우선 목표는 제한시간 안에 교육성과와 업무 적용 가치를 시연으로 증명해 수상 경쟁력을 높이는 것이다. 공식 시상·교육 취지와 사용자 요구를 먼저 확인하고, 확인 사실과 전략적 가정을 구분하라. Agent, RAG, MCP, 멀티모델 비교, 신뢰성 검증을 하나의 업무 흐름과 실제 증거로 연결하라. 심사위원에게 무엇을 어떤 순서로 보여줄지 정한 뒤, 그 장면을 만드는 가장 작은 기능부터 구현하라. 전체 기능을 상세 설계한 뒤 한꺼번에 만들지 말고, 짧은 설계 → 구현 → 실제 실행 → 시연 확인을 반복하라. 상황실장과 요원의 지시·보고, 사용자 자료 제공, 상황 변화에 따른 재지시를 조기에 연결하라. 외부 데이터 API는 무료 기상만 사용하고 선박 API를 추가하지 마라. 상황·명부·기상은 일반 DB, 지침 검색은 벡터DB로 분리하라. 매 반복에서 작동 결과, 교육요소, 시연 증거, 남은 문제를 보고하라. 발표자료와 리허설을 개발과 함께 준비하고 마지막 정상 시연 버전을 보존하라. 모의 기능과 실제 기능을 구분하며, 핵심 교육요소를 조용히 생략하거나 미구현 기능을 구현했다고 표현하지 마라. 불필요한 설계 문서, 추상화, 전면 재작성, 반복 확인 질문으로 진행을 늦추지 마라.

## 17. 현재 코드 기준 개발 규칙

다음 작업은 13번 문서의 미완료 차이를 읽고 시작한다. 현재 스택은 Python HTTP·SQLite·HTML/CSS/JavaScript다. 단순 문구 교체를 실행 구조 변경으로 보고하지 않는다.

상황실장의 첫 단계는 범위 확인·배정에 집중하도록 개선하고 전문 판단은 요원에게 맡긴다. 요원의 정보요구는 이유·출처를 보존해 사용자에게 전달한다. 핵심 질문·제안은 1~2개로 추려야 하며 배열 앞 2개 표시만으로 선정 품질을 입증하지 않는다.

LIVE/DEMO 표시는 보존하고 모델명은 화면에 다시 넣지 않는다. 세션별 상태·삭제·늦은 보고·고정 화면을 함께 검사한다. 기본 매뉴얼은 제공 근거이지 승인된 기관 SOP가 아니다. 키·원본 환경설정을 문서나 도구 출력으로 읽어내지 않는다.

현재 핵심 회귀 명령과 저장 시나리오 판정은 13 §8 및 prototype/PROGRESS.md를 따른다. 새 검증 기록은 단위/HTTP/브라우저/LIVE를 구분한다. 앱 내부 요원 병렬 실행 요구를 코딩 보조 에이전트의 추가 생성 허가로 해석하지 않는다.
