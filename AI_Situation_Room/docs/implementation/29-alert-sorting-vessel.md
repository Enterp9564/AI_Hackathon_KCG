# 주요 알림 정렬·필터와 선체경사 경고

2026-09-29 구현. [P0](28-main-alerts-p0.md)의 환자 목록을 환자·선박 통합 목록으로 확장했다. 최신 사용자 요구에 따라 기존 수신 순서 유지보다 선택한 컬럼 정렬을 우선한다.

## 화면 계약

- 기본은 최신순이다. 환자는 분석 완료 시각 `finished_at`, 선박은 경고 발생 시각 `raised_at`을 사용하고 화면에 기준을 표시한다. 수신 시각으로 오래된 경고를 최신으로 만들지 않는다.
- 이름/대상·상황·내용·시간 헤더는 버튼이다. 같은 헤더를 다시 누르면 오름차순/내림차순이 바뀐다. 다른 컬럼은 오름차순, 시간은 내림차순으로 시작한다. 선택·방향은 화살표와 접근성 이름으로 제공한다.
- 시간은 실제 시점으로 비교하며 결측/잘못된 시각은 양방향 모두 끝에 둔다. 문자열은 한국어·숫자 정렬을 사용한다. 동률에는 식별자로 순서를 고정한다.
- 유형은 전체/환자/선박, 상태는 미열람·환자 즉시조치·상태변화·선박 각도 도달/급변/측정 지연/출처 미확인 기록 등으로 좁힌다. 검색과 필터는 함께 적용된다. 유형 변경 시 상태 필터는 전체로 초기화한다.
- 새 수신 시 현재 정렬을 다시 적용한다. 선택한 원문 판본·상세 펼침·행 포커스는 유지한다. 새 판본은 미열람과 버튼 강조를 다시 켠다.
- 선박 상세에는 원문 제목/내용/근거/주의/기준, 현재·이전 각도와 측정 시각, 경고 시각, 출처 확인 집계를 표시한다. 이 단계의 선박 상세에는 AI 검토 버튼이 없다.

## 수신·저장·API

`linkone_alert_source.py`가 기존 환자 워커의 같은 연결에서 `vessel_alerts.read_vessel_poll`을 호출한다. 조회 주기는 기존 3초이며 브라우저 수에 비례해 DB 연결을 만들지 않는다. [실제 DB 계약](../contracts/linkone-vessel-alerts.md)의 허용 필드만 받는다.

원격 조회는 사건별 최신 101건으로 변경 지문·용량을 확인하고 변경 사건만 본문을 받는다. 화면/저장은 최신 100건이며 초과 안내를 제공한다. 지문 키는 `vessel:` 접두사로 환자와 분리한다. 전체 조회 1,000행/1MB 한도, 정제 후 항목당 24KB 한도를 적용한다. 선박 조회는 savepoint로 분리하여 선박 테이블 오류가 정상 환자 수신을 취소하지 않게 한다.

SQLite `vessel_alerts`에는 세션·출처 ID·허용 원문 해시별 판본과 현재 여부, 수신/열람 시각을 저장한다. 동일 판본 재수신은 중복 생성하지 않는다. `vessel_alert_state`는 마지막 성공/오류/초과 상태를 보존한다. 변경 없는 성공은 메모리 시각만 갱신하고 반복 디스크 쓰기를 줄인다. 재시작 시 이전 기록을 유지하며 새 조회 전에는 대기로 표시한다.

기존 `GET /api/sessions/{sid}/patient-alerts` 응답의 환자 필드는 유지하고 `vessel` 객체에 `items`, `unread`, `status`, `last_success_at`, `error`, `truncated`, `missing_count`, `limit`를 추가한다. 선박 행 열람은 기존 쓰기 토큰/출처 검사 아래 `POST /api/sessions/{sid}/vessel-alert-seen`에 `id`를 보낸다. 다른 세션/연결 사건의 ID는 거절한다.

해온의 읽음은 로컬 기록이다. Link-One 확인 API/DB 쓰기를 호출하지 않는다. 출처 확인자가 있다고 위험 해소로 판정하지 않는다. 조회 범위 밖으로 사라진 기록도 해소로 바꾸지 않고 이력을 보존한다. 환자/선박 수신·정렬·열람은 상황 장부를 변경하거나 요원을 실행하지 않는다.

## 파일 책임

- `prototype/vessel_alerts.py`: 원격 제한 조회, 정제, 판본·열람·수신 상태 저장.
- `prototype/patient_alerts.py`: 공통 워커에서 두 수신 종류 조립, 사건 격리와 실패 처리.
- `prototype/static/alert-list.js`: 통합 항목·정렬·헤더·선박 상세.
- `prototype/static/patient-alerts.js`: 필터·목록·요약·강조·열람 흐름.
- `prototype/server.py`: 정적 스크립트와 열람 API 경로.

## 검증과 한계

- 단위/HTTP: Python 179개 실행, 4개 skip, 나머지 통과. 사건 격리·재시작·중복·원격 확인 미변경·선박 실패 중 환자 수신·토큰/다른 사건 거절을 포함한다.
- JavaScript: 전체 22개 통과. 시간/문자 양방향·결측 마지막·유형 필터·선박 열람 경로를 포함한다.
- 격리 Chrome: 환자 8명+선박 2건에서 최신순/컬럼 전환/유형·경고 필터/상세/모바일 확인. 기존 환자 브라우저 회귀에서 헤더 추가로 8번째 행이 잘리는 실패를 발견하고 행·헤더 간격 수정 후 전체 통과했다. 초안·세션·판본 상세·키보드·대형 화면 회귀도 통과했다. 시험의 AI 실행은 0건이다.
- 실제 읽기 전용 선박 조회: 연결 사건 2개, 첫 조회 19건/250.41ms, 이후 두 조회는 본문 0건/175.97ms·209.75ms. 3초 간격으로 실행했다. 이는 특정 시점의 경고 이력과 조회 지연이며 현재 위험 건수나 장시간 성능 보장이 아니다.
- 실제 새 경고 생성부터 화면 도착까지의 종단 지연, 장시간 동시 사용, 이번 변경의 Safari 검증은 미실시다. LIVE 모델 호출도 실행하지 않았다. Link-One 계정별 미확인 큐와 해온 로컬 읽음은 서로 다르다.

## 재현

프로젝트 루트에서 README의 Python 테스트 명령과 `node --test prototype/tests/test_*.cjs`를 사용한다. 브라우저 시험은 Playwright가 있는 Node 환경에서 `node prototype/tests/browser_vessel_alerts.cjs`, `node prototype/tests/browser_patient_alerts.cjs`다. 시험 서버는 임시 DB·가상 수신만 사용한다. 실행 중인 앱은 변경된 Python 모듈 적용을 위해 동일 DB·모델 키·매뉴얼 설정으로 재시작해야 한다.


### 실행 서버 적용 확인

8860/8861의 AI 실행·링크온 수동 수신 유휴를 확인한 뒤 같은 DB로 재시작했다. 세션 13개/1개, LIVE on, 매뉴얼 off/hybrid(벡터 준비 완료), MCP off를 유지했다. 새 정적 파일의 HTTP 본문 일치를 확인했다. 8860의 연결 사건 2개에서 환자·선박 모두 ready이며 선박 경고 기록은 각각 11건/8건 수신됐다. 8861은 미연결 가상 세션으로 수신 대상이 없다. 병행 작성된 발표 인계 문서 변경은 덮어쓰지 않았다. 원문·비밀 값은 검증 출력에 포함하지 않았다.
