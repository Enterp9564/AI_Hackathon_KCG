# 해온 → 링크온 접속 준비 회신

작성일: 2026-09-28  
제목: HAEON(해온) 개발용 DB 접속 준비 및 조회 기준 회신 확인

갱신: 링크온의 공개키·변경 신호·조회 기준 후속 회신을 반영했습니다. 아래 확정 사항은 담당자 회신 기준이며 실접속 검증 결과는 아닙니다.

안녕하세요. 해온 개발팀입니다.

전달해 주신 링크온 DB 스키마와 SSH·DB 접속 정보를 확인했습니다. 링크온의 시험 데이터를 읽어 해온의 상황 분석에 활용하는 개발 연동을 준비하겠습니다.

## 1. 이번 연동 범위

- 링크온 → 해온 방향의 읽기 전용 연동으로 진행합니다.
- 해온에서 링크온 DB를 수정하거나 데이터를 입력하는 API를 요구하지 않습니다.
- 해온의 분석 결과는 우선 해온 화면에서 활용합니다. 결과를 링크온으로 제공하는 기능은 이번 접속 범위에 포함하지 않습니다.
- 기존에 전달받은 스키마·테이블 자료와 DB 비밀번호는 다시 보내지 않으셔도 됩니다. 비밀번호는 이 문서에 기재하지 않습니다.

## 2. 전달받은 접속 조건 확인

### SSH

- 서버: `114.110.181.118`
- 포트: `10022`
- 계정: `linkone-link`
- 인증: Ed25519 공개키
- 허용 용도: VM 내부 `127.0.0.1:5432`로 연결하는 SSH 포트 포워딩
- 셸 접속·VM 명령 실행: 제공하지 않는 것으로 확인했습니다.
- VPN·접속 IP 등록: 필요 없는 것으로 확인했습니다.
- 서버 ED25519 호스트키 지문: `SHA256:RbdRpHgQVia1Ic9ZNRS0qLY9skVG24sCRkwYQse8QZ4`

최초 연결 시 전달받은 서버 지문과 실제 지문을 대조하겠습니다.

### PostgreSQL

- 버전: PostgreSQL 16.15
- DB: `linkone` / 스키마: `public`
- 계정: `linkone_ro`
- 서버 내부 접속 대상: `127.0.0.1:5432`
- 해온 Mac의 터널 접속 주소: `127.0.0.1:15432` 예정
- TLS: 전달해 주신 조건에 따라 SSH 터널 안에서 `sslmode=disable`로 초기 접속을 확인할 예정입니다.
- 계정 만료: 현재 없음. 종료·폐기 시점은 추후 협의합니다.

서버 SSH 지문 일치와 변경 신호 API 응답은 확인했습니다. 등록 후 SSH 인증과 DB 연결·읽기 점검도 성공했습니다.

## 3. 공개키 전달과 등록

해온 전용 SSH 키를 생성했습니다. [공개키 등록 요청](linkone-access/PUBLIC_KEY_REQUEST.md)과 [공개키 파일](linkone-access/haeon_linkone_ed25519.pub)에 공개키·SHA256 지문을 준비했습니다. 개인키는 해온 개발 장비에만 보관합니다.

공개키 한 줄과 SHA256 지문을 함께 전달하면 링크온 측에서 지문 대조 후 등록하고 완료를 회신하는 절차로 확인했습니다. 전달 경로는 회신에 `[예: 현재 연락 중인 채널로 보내 주십시오]`라고 기재되어 있어 구체 담당자는 확정되지 않았습니다. 공개키 전달 시 현재 채널의 담당자를 확인하겠습니다.

공개키 전달 파일을 준비했고 사용자가 송신 완료를 확인했습니다. 등록 완료 회신을 받았으며 이후 SSH 터널과 읽기 전용 DB 접속에 성공했습니다. 등록 후 SSH 터널 및 DB 접속 재시험은 성공했습니다. 등록 전 사전 SSH 인증 시험은 거절됐던 이력으로 보존합니다.

## 4. 초기 조회 대상과 조회 방식

첫 시험은 다음 훈련 사건으로 진행할 예정입니다.

- 사건명: `(훈련) 낚시어선 충돌`
- `room.id`: `4957a3fb-b012-4e9a-87e1-57b4301cf6b9`
- 사건번호: `JJ-DRILL-2026-03`

우선 조회할 정보는 다음과 같습니다.

- `room`: 사건 식별자·사건명·실상황/훈련·진행 상태·신고 인원
- `person`: 대상자 식별자·명부 포함/제외·병합·미탑승 정보
- `person_state`: 현재 구조·이송·관리·중증도·위치
- `person_event`: 원본 현장 기록·정정·취소·서버/단말 시각
- `transfer`: 인계 지정·인수·거절·해제·종결

기본 연결을 확인한 뒤 `transport_order`, `no_accept`, `hull_tilt`, `roster_upload` 등으로 확대하겠습니다.

조회 시에는 다음 조건을 적용하겠습니다.

- 초기 변경 확인 간격은 **5초**로 링크온 측의 확인을 받았습니다. 정상 운용 중 변경 신호가 달라질 때 필요한 DB 자료를 조회합니다. 최초 연결·재연결 시에는 기준 상태를 확인합니다.
- 개별 조회 결과는 최대 **1,000건**으로 제한합니다. 후속 페이지도 연속 폭주하지 않도록 간격을 두겠습니다.
- 컬럼을 명시하며, 조회가 금지된 `account.password_hash`, `device_credential.token_hash`, `auth_session.token_hash`, `band.secret`은 요청하지 않습니다.
- 초기에는 음성·사진·도면 원본 및 분석에 불필요한 개인정보·다운로드 토큰을 가져오지 않습니다.
- 사건별 조회는 해당 테이블의 `room_id`를 사용하고, `room` 자체는 `id`로 조회합니다.
- 해온에는 원본 식별자·출처·자료 시각을 함께 보관하고, 링크온 사건 ID와 해온 세션 ID를 연결합니다.
- 문서의 인원 집계·병합·취소 규칙을 확인한 뒤 집계합니다. 단순 행 수를 구조 인원으로 사용하지 않습니다.

## 5. 후속 회신으로 확인된 조회 기준

### 변경 신호 API

- 주소: `https://114-110-181-118.sslip.io/api/sync`
- HTTP GET, 인증 불필요. 데이터 본문 없이 변경 번호를 반환합니다.
- `?rooms=<room.id>,<room.id>`로 최대 20개 사건을 지정할 수 있습니다.
- `all`: 서버 전체 변경 번호. `rooms[id]`: 사건별 변경 번호. `web`: 화면 판 이름으로 해온에서는 사용하지 않습니다.

링크온이 전달한 응답 예제이며 이번에 실호출한 결과는 아닙니다.

```json
{"all":"b4acf3a3.24","rooms":{"4957a3fb-b012-4e9a-87e1-57b4301cf6b9":"b4acf3a3.0"},"web":"index-D3yKaSyi.js"}
```

번호는 숫자 크기로 비교하지 않고 **전체 문자열이 이전 값과 다른지** 비교합니다. QR 팔찌 연결 등 일부 쓰기는 `all`만 바뀌므로 `all` 또는 해당 `rooms[id]` 중 하나라도 달라지면 지정 사건을 재조회합니다.

링크온 서버를 통한 성공한 쓰기는 변경 번호를 갱신합니다. 조회·실패한 쓰기·시간 경과에 따른 잠금 만료는 번호를 바꾸지 않습니다. DB 직접 수정도 이 신호로 감지된다고 가정하지 않습니다.

재시작하면 번호 앞부분이 바뀌고 카운터가 초기화됩니다. 접두부 변경, 최초 연결, 재연결 시 지정 사건의 기준 상태를 다시 읽겠습니다. 전체 기준 상태는 DB 33개 표 전체의 무조건 복사를 뜻하지 않습니다.

### 이력과 현재 상태

- `person_event`: `server_at >= 마지막으로 읽은 server_at - 30초` 범위를 겹쳐 조회하고 ID로 중복을 제거합니다. ID 발급과 커밋 순서가 다를 수 있으므로 `id > 마지막 ID`만 사용하지 않습니다.
- `activity_log`도 `server_at`을 사용하지만, 다른 이력 표는 실제 시간 컬럼에 맞춥니다. 예를 들어 `room_closure.at`, `hull_tilt.measured_at`을 동일 이름의 컬럼으로 취급하지 않습니다.
- `person_state`: `updated_at` 기반 변경 조회가 가능하며 `last_event_id`는 상태를 만든 마지막 이벤트 ID입니다. 동시 커밋과 같은 시각 경계는 중복 허용·재대조로 처리할 예정입니다.
- `person`, `transfer`: 수정 시각 컬럼이 없으므로 신호가 달라지면 지정 사건의 필요한 행을 다시 읽습니다.
- 인적사항 정정은 `person_event.IDENTITY`에도 남습니다.
- 정상 조회 결과와 페이지를 모두 저장한 뒤 마지막 조회 기준을 갱신합니다. 실패하거나 일부 페이지만 받은 상태에서 기준을 앞당기지 않습니다.

**30초 중복 조회의 적용 한계:** 링크온은 트랜잭션이 대개 1초 이내라고 설명했습니다. 최대 지연 30초 이하를 보장한 것은 아니므로, 이 방식만으로 무누락을 보장한다고 표현하지 않습니다. 구현 시 주기적인 지정 사건 전체 이력 재대조를 보완책으로 검토합니다. ID 중복 제거는 누락 탐지와 별개입니다. 신호 조회 전후에 변경이 생긴 경우에도 재조회가 이어지도록 하며, 여러 페이지에 걸친 조회의 일관성을 검증해야 합니다.

### 상황 종결과 재개

재개를 지원하며, 기존 스키마의 “되돌릴 수 없음”은 오래된 설명으로 확인됐습니다.

- 종결 승인: `room_closure.APPROVE` 기록, `room.status=CLOSED`, 이후 기록 쓰기 차단
- 재개 권한: 개설 관서 또는 종결 승인 관서, 사유 필수
- 재개 결과: `room_closure.REOPEN` 추가, `room.status=ACTIVE`, `closed_at`·`close_reason` 비움
- 종결·재개 이력은 삭제하지 않고 `room_closure`에 보존

전달받은 원본 스키마 파일은 변경하지 않았습니다. 위 설명은 후속 회신으로 확인한 정정 사항입니다.

## 6. 준비 및 확인 순서

1. 해온: 전용 SSH 키 생성 및 공개키·지문 전달
2. 링크온: 공개키 등록 후 완료 회신
3. 해온: 서버 지문 확인 → SSH 터널 연결 → 읽기 전용 DB 인증
4. 해온: 권한 메타데이터와 테스트 사건의 소량 데이터 확인. 쓰기 명령으로 권한을 시험하지 않음
5. 해온: 확인된 변경 신호·종결/재개 기준 검증 및 실제 집계 규칙 대조
6. 해온: 수신 데이터 변환 및 상황 분석 연결 구현·검증

현재 공개키 전달 파일·로컬 접속 설정·DB 조회 도구 준비를 마쳤습니다. 공개키 등록·SSH 인증·DB 소량 조회는 완료했으며 해온 자동 수신은 아직 구현하지 않았습니다. [실행 안내와 점검 결과](linkone-access/README.md)를 참고하십시오.
