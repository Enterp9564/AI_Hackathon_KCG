# 검증요원 ON/OFF — 가능성 검토와 설계안

> 후속 상태: 같은 날 사용자의 구현 승인 후 8860에 적용했다. 아래는 설계 당시 기록이며, 실제 동작·검증은 [상세 구현](../../implementation/36-critic-toggle.md)을 따른다.

**상태: 계획·미구현.** 2026-09-30 사용자의 구현 계획 재작성 요청에 따라 코드 흐름을 읽고 설계만 작성했다. 앱·설정·실행 서버는 변경하지 않았다.

## 1. 목적과 가능성

현재 `Engine.process`는 전문요원 보고를 모은 뒤 검증요원을 호출하고, 그 결과를 기다린 다음 상황실장의 최종 종합을 실행한다. 설정을 추가해 이 별도 호출을 생략하는 것은 가능하다. 난이도는 낮음~중간이다. 조건 분기 자체보다 대기 중 요청의 설정 고정, 여러 수신 경로, 화면의 ‘검증 대기/완료’ 표시를 일치시키는 작업이 중요하다.

상황실장도 보고의 충돌·미확인 사항을 검토하지만 검증요원은 별도 호출로 근거·누락·모순을 점검한다. 기능이 겹치는 부분은 있으나 OFF가 ON과 동일한 검토 품질이라는 근거는 없다. OFF 시 상황실장의 기존 최종 종합에서 이 항목을 확인하도록 짧게 명시하고, 추가 모델 호출이나 검증요원의 전체 프롬프트 복사는 하지 않는다.

[기존 1회씩의 훈련 벤치마크](../../implementation/33-linkone-llm-benchmark.md)에서 검증 단계는 OpenAI 39.706초, 로컬 Qwen 28.342초였다. OFF이면 이 호출은 없어지지만 종합 입력·응답 시간이 달라지므로 해당 시간만큼 전체가 정확히 빨라진다고 보장하지 않는다. 이번 계획에서는 새 LIVE 벤치마크나 자동 성능 측정을 수행하지 않는다.

## 2. 설정 계약

- 위치: 기존 우측 상단 설정 창에 ‘검증요원 사용’ ON/OFF 스위치 추가. 모델 선택·국제 SAR 검색과 독립된 항목이다.
- 기본값: **ON**. 기존 저장 DB에 설정이 없으면 현재 동작을 유지한다. 사용자가 OFF로 저장하면 재시작 후에도 유지한다.
- 범위: 해당 해온 서버 DB의 모든 세션. OpenAI·로컬 LLM·DEMO에 같은 흐름을 적용한다. 별도 DB인 8860과 8861의 설정은 독립적이다.
- 적용: **새 요청 접수부터 적용**. 이미 접수된 대기·실행 중 요청은 당시 설정을 유지한다. 실행 중에도 스위치는 바꿀 수 있으나 현재 호출을 취소하거나 이미 접수된 요청을 수정하지 않는다.
- SQLite `settings`의 `critic_enabled` 키에 JSON boolean 저장. 입력은 실제 boolean만 허용한다. 문자열 `"false"`, 숫자, null 등은 거부한다.
- `GET/POST /api/settings/critic` → `{enabled: boolean, scope: "server", applies_to: "new_requests"}`. POST 본문은 `{enabled: boolean}`. 기존 Host/Origin·토큰 검사를 그대로 적용한다.
- 새 run에는 `critic_enabled`를 최초 `_enqueue` 트랜잭션에서 저장한다. 일반 채팅·MCP 인용·Link-One 동기화/재분석이 모두 이 경로를 거치도록 확인한다. 같은 request_id 재요청은 기존 run의 설정을 유지한다.
- 서버의 전역 설정을 매 단계 다시 읽지 않는다. 이전 run에 필드가 없으면 실행 호환 기본값은 ON이지만, 과거 보고를 덮어쓰거나 실제 검증 수행 여부를 추정해 ‘완료’ 표시하지 않는다.

## 3. 실행과 기록

```text
ON : 상황실장 배정 → 전문요원 보고 → 검증요원 → 상황실장 종합
OFF: 상황실장 배정 → 전문요원 보고 ─────────→ 상황실장 종합
```

OFF일 때 검증요원의 task, model call, 보고, SAR 검증 문맥을 만들지 않는다. 전문요원 보고 수집 후 run에 `critic_review={status:"skipped",reason:"disabled_by_setting"}`를 저장하고 같은 내용을 서버 이벤트로 남긴다. 가짜 완료 보고나 0초짜리 호출은 기록하지 않는다.

ON일 때 전문요원 보고 이후 `critic_review.status`는 `running` → `completed` 또는 `failed`다. 기존 검증 실패는 기존대로 분석 실패로 남기며 OFF로 자동 전환하지 않는다. 검증에 도달하기 전 상태는 `pending`이다. 전문요원 없이 직접 접수·반영하는 기존 경로는 ON/OFF와 관계없이 `not_applicable`이며, 검증을 수행한 것으로 표시하지 않는다.

상황실장 최종 입력에 `review_policy={critic_enabled,critic_status}`를 제공한다. OFF이면 기존 최종 호출에 ‘별도 검증요원 검토는 생략됐으므로 제공된 전문요원 보고의 근거·충돌·미확인 사항을 확인하고, 별도 검증 완료로 표현하지 않는다’는 짧은 지침을 추가한다. 최종 저장 데이터의 검증 상태는 모델 응답이 아닌 서버 기록으로 결정한다.

기존 JSON 형식 검사, 근거 ID 검사, 매뉴얼 인용 연결 검사, 지역별 자원 제한, 세션 격리는 ON/OFF에 관계없이 유지한다. 검증요원 OFF는 코드가 수행하는 검사를 끄는 설정이 아니다. 상황실장 자체를 끄는 기능도 이번 범위에 없다.

## 4. UI 계약

- 설정 안내: ‘이 서버의 새 요청부터 적용됩니다. 이미 진행·대기 중인 요청은 접수 당시 설정을 유지합니다. 끄면 전문요원 보고 후 상황실장이 바로 종합합니다.’
- 저장 성공 후 스위치와 안내를 갱신한다. 실패하면 이전 값으로 복원하고 오류를 표시한다. 모델 설정 폼·채팅 초안은 유지한다.
- 실행 화면은 선택한 run의 설정·실제 상태를 따른다. 현재 전역 스위치로 과거 보고를 재해석하지 않는다.
- OFF 실행에서는 ‘검증요원 생략 · 설정 OFF’를 표시한다. 전문요원 종료 뒤 ‘검증 대기’에 머물지 않고 ‘상황실장 종합’으로 전환한다.
- 최종 완료 문구는 ‘전문요원 보고를 종합했습니다. 별도 검증요원 검토는 생략했습니다.’로 표시한다. ON 완료에만 실제 검증 반영 문구를 쓴다. 직접 처리 경로는 별도로 구별한다.
- 최종 보고 상세·실행 이력에도 실제 검증 상태를 표시한다. 미호출 검증요원의 시간축 막대나 근거 목록을 만들지 않는다.
- 오래된 실행은 실제 task/call 기록으로 검증 상태를 표시한다. 자료가 부족하면 미확인으로 두며 현재 ON/OFF를 대입하지 않는다.

## 5. 검증과 적용 범위

격리된 SQLite·가짜 모델로 ON/OFF 호출 순서, 설정 지속, 접수 중 설정 변경, 중복 request_id, 직접 처리, 검증 실패를 확인한다. HTTP·브라우저에서 저장 실패 복원과 생략 표시를 확인한다. 실제 모델의 품질 동등성이나 시간 단축 비율을 이 시험으로 주장하지 않는다.

기존 검증요원 프롬프트·토큰 예산·모델은 ON 경로에서 유지한다. 새 역할·프레임워크·성능 수집기를 추가하지 않는다. 두 기능은 독립적으로 구현 가능하며, 수신 주기 변경이 AI를 실행하거나 검증 설정을 바꾸지 않는다.
