# Link-One 현재 상태 주기 수신 — 가능성 검토와 설계안

> 후속 상태: 같은 날 사용자의 구현 승인 후 8860에 적용했다. 아래는 설계 당시 기록이며, 실제 동작·검증은 [상세 구현](../../implementation/35-linkone-current-state.md)을 따른다.

**상태: 개정안·미구현.** 2026-09-30 사용자 요청에 따라 읽기 전용 조사와 계획 작성만 했다. 서버 코드·갱신 주기·DB 구조·실행 설정을 변경하지 않았으며 재시작도 하지 않았다.

## 이번 개정의 결정

- 정상 연결 시 **환자·선체 경고 조회는 2초, 현재 상황·명부·현장기록 조회는 3초 고정**으로 제안한다. 브라우저는 해온 캐시를 1초마다 읽는다.
- 이전의 부하 결과에 따른 5초 전환안과 상시 성능 통계·자동 주기 조절안은 제외한다. 운영 프로그램에 부하 측정 서비스, 추가 DB 진단 쿼리, p95 계산, 자동 벤치마크를 넣지 않는다.
- 검증요원 ON/OFF는 별도 [설계](2026-09-30-critic-toggle-design.md)와 [구현 계획](../plans/2026-09-30-critic-toggle.md)으로 분리한다. 이번 요청은 두 기능 모두 계획 작성에 한정된다.

## 1. 확인한 지연 경로

현재 응급 판정 알림은 `patient_alerts.INTERVAL=3`으로 서버가 조회한다. 브라우저는 로컬 알림 API를 1초마다 읽는다. 반면 우측 현재 상황·승선원 명부는 `LinkOneSync`가 수동 수신한 불변 수신본을 사용한다. `/api/sessions/:id`를 1초마다 읽어도 원격 명부가 새로 수신되지는 않는다. 수동 동기화는 전체 11개 표 수신 후 변경이 있으면 AI 분석까지 접수하므로 이를 3초마다 호출해서는 안 된다.

최근 제주호 훈련의 사용자 지목 대상자에 대해 본문·음성 파일을 출력하지 않고 시각과 ID만 대조했다. 동일 이름의 과거 KISTI호 대상자는 다른 사건이므로 제외했다.

| 단계 | 확인 시각(KST, 2026-09-30) | 관측 의미 |
|---|---|---|
| 음성 현장기록 저장 | 16:32:17.693 / 16:32:17.787 | RECORD/VOICE 2건이 person_event에 저장 |
| 링크온 AI 판정 완료 | 16:34:52.034 | 마지막 위 기록 기준 약 154.247초 뒤 |
| 해온 수신본 3 | 16:40:31.614 | 위 2건이 해온 전체 수신본에 처음 포함, 약 493.827초 뒤 |
| 이송 인수 상태 저장 | 16:42:58.388 | person_state 변경 |
| 해온 수신본 4 | 16:47:10.098 | 해당 상태가 처음 포함, 약 251.710초 뒤 |

음성 기록의 client_at→server_at 차이는 두 건 모두 약 0.2초 이내였다. voice_note에 저장된 처리 latency_ms는 4,722ms였으나 이 값의 전체 녹음/분류/저장 구간 정의는 확인하지 않았으므로 총 사용자 체감 시간으로 단정하지 않는다. 약 154초는 기록 시점→AI 판정 완료 차이이며 대기열과 생성 시간을 분리 측정한 값이 아니다. 약 494초는 해온 저장 시점까지의 차이로, 원격 전송 자체가 8분 걸렸다는 의미가 아니다. 최종 수신본 5에는 변경 상태가 이미 들어와 있었다.

## 2. 가능성 판단

**구현 가능성이 높다. 난이도는 중간이다.** 기존 읽기 전용 접속·영구 연결 워커·3초 알림·세션별 저장·상태 집계 코드를 재사용할 수 있다. 어려운 부분은 조회 주기보다, 최신 표시와 이전 자료로 작성된 AI 보고를 혼동하지 않게 하는 것과 명부 정정·취소·세션 전환을 처리하는 것이다.

현재 상태 조회는 3초로 고정하고, 기존 환자·선체 알림 조회를 3초에서 2초로 줄이는 것은 코드 구조상 가능하다. 같은 조회 범위라면 알림 조회 사이클은 분당 20회에서 30회로 **50% 증가**한다. 현재 상태 조회 20회를 더하면 서버당 정상 상태의 워커 사이클은 분당 약 50회다. 이는 SQL 문장 수나 CPU 사용량이 아니며, 사이클당 여러 쿼리가 실행될 수 있다. 브라우저 탭 수와 무관하게 서버별로 사건을 중복 제거하고, 두 서버를 켜면 원격 조회도 각 서버에서 발생한다.

상시 부하 측정을 없애는 것과 원격 조회 비용이 작다는 것은 별개다. 기존 조회 시작·완료 시각 기록은 유지하되 추가 진단 쿼리·통계 수집·자동 조절을 만들지 않는다. 2초 조회가 DB 부담 없이 동작한다고 아직 실증한 것은 아니다. 대신 응답 크기 제한, 무변경 저장 생략, 영구 연결 재사용, 조회 중첩 방지로 비용을 제한한다.

**주기는 화면 반영 보장 시간이 아니다.** 정상적인 짧은 조회라면 알림은 최대 약 2초의 다음 조회 대기와 약 1초의 화면 조회 대기에 통신 시간이 더해진다. 현재 상태는 각각 약 3초와 1초다. 링크온 DB 저장 이전의 음성 전사·분류·AI 판정 지연은 줄이지 못한다. 별도 p95 합격 기준이나 운영 중 성능 계산은 두지 않고, 구현 시 격리 환경에서 갱신·무중첩·호출 횟수만 확인한다.

## 3. 제안 구조

```text
링크온 person / person_state / 확정 저장된 RECORD
                  ↓ 3초, 읽기 전용·변경 감지
해온 현재 상태 캐시 + 변경된 판본 보존
                  ↓ 로컬 API
현재 상황 숫자 + 최신 명부/환자 상태 + 최근 현장기록

수동 전체 동기화 → 분석용 수신본 → 사용자 요청에 따른 기존 AI 흐름
```

현재 상태 수신은 기존 응급 알림과 독립된 워커로 둔다. 영구 SSH/Postgres 연결의 제한·종료 코드는 재사용하되 연결/장애/백오프 상태는 분리한다. 추가 조회 실패로 응급 알림의 수신까지 멈추게 하지 않는다. 알림의 정상 주기는 2초로 바꾸되 기존 오류 백오프 6→12→24→48→60초는 유지한다. 고정 주기는 정상 상태에 적용하며, 장애나 느린 조회 때 겹친 요청으로 주기를 억지로 맞추지 않는다. 여러 해온 서버(8860/8861)는 각각 워커를 가진다. 별도 상시 측정기를 추가하지 않으며, 격리 시험에서는 서버 수만큼 조회가 발생하고 탭 수로는 늘지 않는지 확인한다.

현재 상태는 별도 캐시다. 기존 session.facts/version, 분석용 linkone_snapshots, 실행 중 요원의 context, 이전 보고, 메시지를 자동으로 수정하지 않는다. AI 재실행·질문 생성·출동 제안·원격 DB 쓰기도 발생시키지 않는다. 분석에 최신 전체 정보를 쓰려면 기존 수동 동기화를 실행한다. ‘현재 자료 재분석’은 저장된 분석 수신본을 재검토하는 기능임을 화면에 분명히 쓴다.

## 4. 수신 범위와 데이터 계약

- 대상: 이미 연결된 room_id만. 정상 주기 3초 고정, 서버 실행 옵션은 0(꺼짐)/3초. 실패는 6→12→24→48→60초 백오프, 회복하면 3초로 복귀. 겹친 조회·밀린 조회의 연속 실행 금지.
- 집계 원천: room의 명부 판본과 person의 포함/병합/제외/미탑승/제거 상태, person_state의 구조·중증도·관리·이송·위치·last_event_id·updated_at. 명부 판본 미확보 시 총원은 null로 유지한다. 상태 미기록을 선내 잔류나 특정 중증도로 만들지 않는다.
- 표시: 이름·구분·객실 등 명부 식별 필드, 상태·관리 세력/종결지 이름. 상세 필드는 기존 허용목록을 좁혀 재사용하고 위치 좌표·장비 제원 등 새 범위를 확장하지 않는다.
- 현장기록: person_event의 RECORD만, 확정 저장된 text/category/via와 기록 ID·client/server 시각. AI_ADVICE는 현장 사실에 합치지 않는다. 음성 파일·voice_note.transcript·인증 자료는 주기 수신하지 않는다.
- 최근 기록은 1인당 5건만 표시하고 전체 건수/생략 여부를 명시한다. 취소/정정 연결은 원본 이력의 의미를 먼저 확인한다. 선택된 기록의 취소 참조도 같은 트랜잭션에서 읽고 ‘취소된 기록’을 표시하며 사실로 재사용하지 않는다. 지원하지 않는 취소 연결은 확인 필요로 표시한다.
- 초기 안전 상한: 연결 사건 32개, 조회 응답 전체 명부 2,000명·최근 기록 2,000건·2MB. 초과 시 마지막 정상 자료를 보존하고 수신 범위 초과를 표시한다. 잘린 명부로 정확한 총원이나 0을 표시하지 않는다. 상한 확대는 이번 범위에서 제외한다.
- 일관성: 동일 읽기 전용 repeatable-read 트랜잭션에서 명부/상태/선택 기록을 읽는다. 다른 사건/person 참조, 중복 ID, 파손 데이터는 거부한다. 큰 정수 이력 ID는 문자열로 보존한다.
- 변경 감지: 시각 최대값만 사용하지 않고 표시용 허용 필드 전체의 정렬된 fingerprint로 삭제·정정도 감지한다. 무변경 응답은 fingerprint/checked_at만, 변경 시 상세 자료를 반환한다. 동일 상태의 매 3초 영구 저장 금지. 변경 판본은 기존 원문 기록과 분리해 보존한다.
- 최신 DB 변경 시각·해온 조회 성공 시각·상태가 실제 바뀐 수신 시각을 각각 기록한다. 소스 시각의 미래값/오프라인 값으로 조회 정상 여부를 판단하지 않는다.

## 5. 화면과 AI 근거의 구분

우측 현재 상황의 구조/미구조 집계는 현재 상태 캐시를 우선 표시하고 ‘링크온 현재 상태 ·3초 확인’, 최근 확인 시각, ‘AI 검토 전’을 보여준다. 최초 캐시가 없으면 기존 수신본을 ‘분석용 저장 자료’로 표시한다. 오류·10초 이상 마지막 성공 없음·서버 재시작 뒤 첫 확인 전에는 ‘갱신 지연/확인 대기’와 마지막 성공 시각을 표시하고 0으로 초기화하지 않는다.

기존 승선원 창은 ‘현재 상태’와 ‘분석 수신본·변경 내역’을 구분한다. 열려 있는 현재 상태 보기는 1초마다 로컬 캐시를 읽는다. 원격 조회는 서버가 3초마다 수행한다. 검색·정렬·스크롤·열린 환자 행·과거 판본 선택을 유지하고 다른 사건으로 전환된 뒤 도착한 이전 응답을 버린다. 각 환자의 최근 현장기록에 텍스트/음성 구분과 원본 저장 시각을 붙인다. 알림 AI 판정 완료를 기다리지 않고 이 기록을 표시한다.

현재 상태의 인원/명부/상태/기록 fingerprint와 분석용 수신본의 동일 필드 fingerprint가 다르면 ‘새 현장 정보가 있습니다. 기존 AI 보고는 수신본 N 기준’이라고 표시한다. 비교 불가하면 ‘분석 자료와 최신 상태의 일치 여부 미확인’으로 표시한다. 이전 보고를 자동 수정하거나 최신 검증 완료로 표시하지 않는다. 기존 응급 알림의 판정 내용은 그대로 유지하고 현재 상태/현장기록 보기로 이동할 수 있게 한다.

## 6. 범위 밖과 남은 확인

전체 표 3초 동기화, 자동 AI 분석, 링크온 음성 처리/AI 스케줄 수정, 자동 출동, 다른 프로젝트 송신은 범위 밖이다. 기존 임상 판정의 옳고 그름을 평가하는 작업도 아니다.

구현 전 person/person_state/person_event의 인덱스와 취소/정정 규칙을 읽기 전용으로 확인한다. 정상 주기 2초/3초로 고정하며 5초 자동 전환이나 상시 부하 측정은 구현하지 않는다. 원격 DB의 실제 여유와 핫스팟 품질은 미검증이다. 음성 처리 전체 구간도 DB 메타데이터만으로 분해할 수 없으므로 음성 입력부터 화면까지 2~3초를 보장하지 않는다.
