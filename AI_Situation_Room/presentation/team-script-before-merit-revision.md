# 팀원 설득용 발표 대본

> 15장 · 목표 7분 30초 · 현재 슬라이드의 발표 노트(N)를 옮긴 검토용 대본입니다.
> 시간은 리허설 실측값이 아닙니다. 구현·연동 상태는 발표 전에 실제 결과에 맞춰 갱신합니다.

[발표자료 열기](team.html)

## 01. 함께 만들 프로젝트

**목표 구간: 0:00–0:30**

우리 팀에는 현장 구조, 응급 지원, 상황실이라는 세 가지 프로젝트가 있습니다. 각자 만들고 싶은 기능을 자유롭게 완성하면서, 마지막에는 API로 서로의 정보를 주고받는 하나의 현장 대응 흐름을 만들자는 제안입니다. 개인 프로젝트의 가치와 팀 결과물을 함께 살려 수상 경쟁력을 높이겠습니다.

## 02. 2팀의 역할

**목표 구간: 0:30–1:00**

4번 이미지의 최신 인원 네 명을 기준으로 했습니다. 기존 과제 신청 기준으로 Link-One은 신진섭, RESAID AI는 채민주, AI 상황실은 김대성과 송민주입니다. 이것은 출발점의 역할 구분이며 세부 개발 분담은 팀에서 조정할 수 있습니다.

## 03. 개발 자율성

**목표 구간: 1:00–1:30**

한 프로젝트에 모두의 화면과 코드를 합치자는 뜻은 아닙니다. 각자의 도구와 화면, 핵심 기능을 존중합니다. 결과를 외부로 주고받는 작은 API 접점만 맞추면 팀의 공동 시연을 구성할 수 있습니다. 기존 기능이 먼저 작동하고, 연결은 그 결과 위에 붙입니다.

## 04. 연결이 필요한 이유

**목표 구간: 1:30–2:00**

예를 들어 현장에서 구조 상태를 수정하면 상황실의 인원과 지원 검토도 바뀌어야 합니다. 응급 지원 프로젝트가 추가 확인을 요청하면 그 질문이 현장까지 돌아가야 합니다. 세 프로젝트가 같은 사건의 변화를 이해할 때 연결의 가치가 생깁니다.

## 05. 왕복하는 정보

**목표 구간: 2:00–2:30**

첫 연결 시연은 작게 잡습니다. 현장 보고를 AI 상황실이 받고 필요한 정보를 RESAID AI에 요청합니다. 돌아온 결과와 근거를 종합해 현장에 확인 요청을 보냅니다. 현장의 후속 보고까지 같은 사건으로 연결하면 왕복 흐름을 보여줄 수 있습니다. 실제 외부 API 연결은 아직 구현 전입니다.

## 06. 연결 준비

**목표 구간: 2:30–3:00**

연결 작업은 마지막에 하더라도 접점까지 마지막에 정하면 위험합니다. 지금 사건 ID, 대상자 ID, 출처, 시각, 버전과 결과 형식을 합의하고 예제 JSON을 공유하겠습니다. 동일 이벤트 중복 반영, 이전 버전 충돌, 응답 실패는 연결부에서 다룹니다. 실제 주소와 인증은 아직 정하지 않았습니다.

## 07. 상황실의 판단 구조

**목표 구간: 3:00–3:30**

첨부 스토리의 출발점은 접수부터 대응 방향 도출까지 AI가 상황을 해석하는 구조입니다. 여기서 End-to-End는 업무 흐름이 이어진다는 의미로 쓰겠습니다. 단일 신경망을 종단간 학습했다는 뜻은 아닙니다. 전문요원의 검토와 프로그램의 형식·합계 검사를 거쳐 사람이 판단할 수 있는 제안을 만듭니다.

## 08. 판단의 근거

**목표 구간: 3:30–4:00**

AI가 상황을 해석할 수 있다는 설명 다음에는 그 판단을 어떻게 검토할지 답해야 합니다. 적용 지침, 빠진 정보, 보고 간 충돌을 드러내겠습니다. RAG와 검증요원은 이 문제를 줄이기 위한 설계이며 정확성을 자동 보장하지 않습니다.

## 09. RAG가 맡는 역할

**목표 구간: 4:00–4:30**

RAG는 관련 자료를 검색해 모델이 참고하도록 하는 구조입니다. 현재 앱은 단어 기반 자료 검색이고 벡터 검색은 앞으로 구현해야 합니다. 문서의 버전과 적용 조건도 확인해야 하므로 검색 유사도를 대응의 중요도로 취급하지 않습니다. 실제 검색 구절이 어떤 제안에 쓰였는지 연결해 보여주는 것을 목표로 합니다.

## 10. 복합 사고와 다중 근거

**목표 구간: 4:30–5:00**

한 번의 사고가 한 종류의 매뉴얼에만 들어맞지는 않을 수 있습니다. 충돌, 화재, 인명 구조의 근거를 함께 찾고 현장 정보와 대조하자는 것이 스토리의 핵심입니다. 매뉴얼을 참고한다는 말이 법령이나 필수 절차를 무시한다는 뜻은 아닙니다. 매뉴얼에 없는 조합을 다루는 능력도 별도의 평가가 필요합니다.

## 11. 기술을 증거로

**목표 구간: 5:00–5:30**

점수를 임의로 계산하기보다 기술 평가에서 확인 가능한 증거를 많이 확보하겠습니다. Agent는 지시와 보고, RAG는 검색 근거, API는 세 프로젝트의 실제 송수신으로 보여줍니다. MCP는 일반 HTTP API와 다르므로 실제 프로토콜 호출이 있어야 합니다. 두 모델 비교와 오류 사례도 같은 조건으로 준비해야 합니다.

## 12. 우리 팀의 차별화

**목표 구간: 5:30–6:00**

제공 자료를 보면 다른 팀에도 RAG, 에이전트, 데이터 분석 주제가 있습니다. 그러므로 기술을 사용했다는 말만으로 차별화를 만들기는 어렵습니다. 2팀의 강점은 현장 구조와 응급 지원, 상황실이 같은 사건 안에서 만난다는 구성입니다. 정보 변화가 세 프로젝트의 결과에 반영되는 장면을 증거로 제시하겠습니다.

## 13. 함께 완성하는 순서

**목표 구간: 6:00–6:30**

초기에는 정보 형식과 최소 예제를 맞춥니다. 이후 각자 프로젝트의 핵심을 개발하고, 실제 연결 전에 작은 송수신을 확인합니다. 최종적으로 사건 하나가 왕복하는 흐름을 완성합니다. 연결 장애가 나면 독립 기능을 보여주고, 녹화는 실제 실행 기록임을 밝히겠습니다.

## 14. 개발 지원 약속

**목표 구간: 6:30–7:00**

저는 API 연결 작업이나 개발 관련 지식이 어느 정도 있으니, 마지막 연결 작업과 개발 중 막히는 부분을 최대한 지원하겠습니다. 각자 만들고 싶은 기능을 우선 개발하시면 됩니다. 필요한 정보 형식과 연결 코드, 오류 확인, 공동 시연 준비는 함께 풀겠습니다.

## 15. 팀에 제안할 결정

**목표 구간: 7:00–7:30**

각자의 프로젝트를 살리면서 팀으로서의 완성도도 높이는 제안입니다. 기술 요소를 실제로 보여주고, 현장과 응급 지원, 상황실이 함께 대응하는 흐름으로 수상을 목표로 하겠습니다. 우선 서로 주고받을 정보와 하나의 가상 사고를 정하면 시작할 수 있습니다. 개발과 연결은 최대한 지원하겠습니다.
