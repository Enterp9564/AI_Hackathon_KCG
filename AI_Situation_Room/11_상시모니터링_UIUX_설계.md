## 1. 설계 판단

**사용자가 내린 지시가 누구의 어떤 임무가 되고, 어떤 근거와 보고를 거쳐 최종 답변으로 돌아오는지 한 화면에서 읽을 수 있게 한다.** 평상시에는 조작 없이 상황을 읽고, 작업 중에는 AI 조직 전체의 진행을 관찰하며, 필요한 순간에 담당자가 확인·정정한다.

사용자의 추가 요구에 따라 이전 설계의 ‘상황 중심 + 작은 AI 상태 목록’을 수정한다. 모니터링의 중심은 **사용자 지시 → 상황실장의 배정 → 독립 임무의 병렬 실행 → 요원별 보고 → 종합·검증 → 사용자 최종 보고**다. 현재 상황·확인할 일·기상·연결 상태도 항상 함께 보여준다.

화면을 보는 사람은 다음을 설명할 수 있어야 한다.

1. 사용자가 무엇을 요청했고 상황실장은 무엇을 확인하려 하는가.
2. 어떤 요원에게 무엇을 맡겼으며 배정 이유는 무엇인가.
3. 지금 동시에 진행되는 임무와 선행 결과를 기다리는 임무는 무엇인가.
4. 각 요원이 무엇을 보고했고, 어떤 근거·미확인사항이 남았는가.
5. 상황실장은 어떤 보고를 종합해 사용자에게 무엇을 답했으며 상황·대응안은 어떻게 바뀌었는가.

여기서 ‘전체의 생각을 읽는다’는 것은 **업무 의도·배정 이유·사용 근거·판단 요약·결과의 연결을 읽는다**는 의미로 구현한다. 상황실장과 요원이 공개 설명용으로 작성한 짧은 요약을 실제 지시·보고에 저장한다. 내부 추론 원문이나 존재하지 않는 사고 과정을 만들어 중계하지 않는다. 요약 생성 전에는 ‘배정 검토 중’, ‘분석 중’처럼 확인 가능한 단계만 표시한다.

운영 화면은 고정된 조직 배치 위에 실제 지시·보고 순간을 강조한다. 발표용 3D 표현은 별도이며, 운영 중에도 공간적 연결감은 살리되 글자와 카드가 돌아다니지 않게 한다.

## 2. 적용 범위와 설계 가정

| 항목 | 이번 기본안 | 이유와 한계 |
|---|---|---|
| 사용 환경 | 담당자 PC와 대형 모니터, 같은 PC의 확장 디스플레이·별도 브라우저 창 우선 | 입력 중에도 공유 상황판을 유지할 수 있음. 실제 장비 구성은 확인 필요 |
| 세션·사건 범위 | 여러 독립 세션 생성, 세션당 사건 1건; 상황판은 선택 세션 1개 고정 | 12의 최신 사용자 요구 반영. 여러 사건을 합치는 통합 관제는 후속 범위 |
| 인원·위치·현장 상태 | 사용자 신고·첨부·정정으로 갱신 | AIS·센서·기관 내부망이 없어 현장 상태를 자동 감지하지 않음 |
| 기상 | 실제 연동 후 위치 기반 기상·해상 조회 | 관측과 예측, 자료 기준시각과 조회시각을 구분 |
| 자원 | 가상 로컬 자원표 | 실제 함정 출동·현장 활동을 추적하는 시스템이라고 표시하지 않음 |
| 사용자 | 한 명의 입력 담당자와 상황판 관람자 | 다중 사용자 권한·동시 편집은 추가 설계 필요 |
| 상시 표시 | 근무 중 연속 사용을 목표로 설계 | 24시간 무중단 운영을 검증했다는 뜻은 아님 |

두 화면은 세션별 공통 저장 상태를 읽는 **표시 방식의 분리**다. 같은 세션을 선택하면 같은 사건을 보여주며, 담당자가 다른 세션으로 이동해도 상황판에 고정된 세션은 유지된다. 화면을 열 때 별도의 사건 복사본이나 AI 실행을 만들지 않는다. 같은 PC에서 먼저 검증하고, 다른 PC·스마트TV 접속과 네트워크 공개는 후속 배포 범위로 둔다.

사용 환경이 한 화면뿐이어도 상시 상황판과 담당자 작업 화면을 전환할 수 있게 한다. 모드 전환 때문에 작업·대화·첨부가 초기화되면 안 된다.

## 3. 모니터링이 실제로 감시하는 것

| 대상 | 변화가 발생하는 근원 | 기본 화면에 보여줄 것 | 감시하지 못하는 것 |
|---|---|---|---|
| 사건 상태 | 새 신고, 사용자 정정, 분석이 끝난 자료 | 사건 요약, 출처별 인원, 위치, 불일치, 버전 | 보고가 없는 현장의 실제 변화 |
| 확인할 일 | 규칙 검사, 상황실장 질문, 검증 결과 | 미해결 질문, 영향, 접수시각, 담당자 응답 대기 | 직원이 실제로 조치를 수행했는지 자동 판정 |
| 대응안 | 요원 보고, 종합, 검증, 새 상황 | 최신안, 기준 상황, 재검토 필요 여부, 변경 이유 | 실제 출동·구조 성공 여부 |
| AI 작업 | 작업 큐와 실행 이벤트 | 담당 요원, 현재 임무, 대기 이유, 실패, 경과시간 | 내부 추론 원문, 임의 완료 예상시간 |
| 기상 | 도구 실행 결과 | 항목별 값·단위·자료시각·조회시각·누락 | 실제 측정하지 않은 현장 관측값 |
| 앱 연결 | 화면과 서버의 통신·작업자 상태 확인 | 마지막 동기화, 연결 지연·끊김, 처리 중단 | 브라우저와 OS까지 완전히 멈춘 상태의 자체 경고 |

**‘새 소식 없음’과 ‘수신이 멈춤’을 구별한다.** 연결은 정상이고 사건 변경만 없으면 ‘변경 없음’이다. 통신이 끊겼다면 마지막 화면을 남기되 ‘연결 끊김 — 표시된 상황은 마지막 수신 기준’으로 바꾼다. 화면 시계가 움직인다는 이유로 데이터가 최신이라고 표시하지 않는다.

## 4. 두 화면의 책임

| 구분 | 상시 상황판 · 대형 모니터 | 담당자 작업 화면 · PC |
|---|---|---|
| 주목적 | 함께 보고 현재 상태와 주의점을 즉시 파악 | 자료 입력, 질문 응답, 근거 확인, 복구 |
| 기본 내용 | 지시·배정·병렬 작업·개별/최종 보고 + 핵심 상황·확인사항·연결 | 같은 상황 요약 + 채팅·첨부·지시/보고 근거·확인 목록 |
| 조작 | 확대, 전체화면, 표시 크기 같은 로컬 표시 설정 | 입력·정정·재시도·재조회·사건 전환 |
| 쓰기 권한 | 사건·작업·확인 상태를 바꾸는 동작 없음 | 프로그램이 검사한 뒤 저장 |
| 자동 갱신 | 실행 상태를 읽어 갱신, AI를 호출하지 않음 | 입력 중에도 요약 부분만 갱신 |
| 상세 접근 | 필수 판단정보는 항상 표시 | 선택한 항목의 상세를 오른쪽 패널로 열기 |

작업 화면의 검색·이력 열람·채팅 스크롤이 대형 화면을 흔들면 안 된다. 선택된 사건을 대형 화면에 바꾸는 행위는 별도 ‘상황판에 표시’ 동작으로 한다. 여러 세션 중 한 세션을 고정 표시하며 자동 순환하지 않는다. 담당자 세션 전환만으로 상황판의 표시 세션을 바꾸지 않는다.

읽기 전용은 버튼을 숨기는 것만으로 구현하지 않는다. 모니터링 경로에서는 쓰기·임무 생성·외부 도구 실행 명령을 받지 않는다. 이는 초기 사용 구조이며 인터넷 공개 서비스의 인증·권한 체계를 대체하지 않는다.

## 5. 대형 모니터 기본 배치

설계 기준 뷰포트는 1920×1080이다. 실제 모니터 인치·시청 거리·OS 배율에 따라 현장 확인으로 조정한다. 4K에서는 글자 크기를 절반으로 줄여 정보를 두 배 넣지 않는다.

```text
┌──────────────────────────────────────────────────────────────────────┐
│ 사건 · 상황 버전 · 훈련/운영 · 라이브/재생 · 마지막 동기화             │
├──────────────────────────────────────────────────────────────────────┤
│ 우선 확인: 인원 불일치 / 미해결 건수 / 기존 대응안 재검토 필요          │
├───────────────────────────────────────────────┬──────────────────────┤
│ 사용자 지시: 현재 상황을 정리하고 대응안을 제시 │ 현재 상황            │
│                      ↓                        │ 총원·구조·소재 미확인 │
│ 상황실장: 요청 요약 / 배정 이유 / 보고 수신 현황│ 출처·위치·기상        │
│       ↓ 지시          ↓ 지시         ↓ 지시    │ 자료 기준시각         │
│ [정보요원]       [수색구조요원]   [자원지원요원]│                      │
│ 명부·기상 확인    관련 지침 검색   가용 자원 검토│ 확인할 일·대응안      │
│ 실제 상태        실제 상태       실제 상태    │ 인원 확인 질문        │
│ 보고 요약 ↑      보고 요약 ↑     보고 요약 ↑  │ 기준 S1 / 현재 S2     │
│         상황실장 보고 수신 → 종합 초안        │ 재검토 필요           │
│                   ↓ 검증 지시                 │                      │
│ 검증요원: 선행 대기 / 검토 / 보완 요청·결과    │                      │
│                   ↓                           │                      │
│ 상황실장 → 사용자: 최종 보고 / 근거 / 미확인   │                      │

└──────────────────────────────────────────────────────────────────────┘
```

도식은 배치와 가능한 업무 관계의 예시다. 모든 요청에서 세 요원에게 지시하는 고정 시나리오가 아니다. 상황실장이 선택한 임무와 의존관계만 활성화한다. 미배정 요원도 자리를 유지하고 ‘이번 요청 배정 없음’으로 표시한다.

| 영역 | 제안 비중 | 상시 표시 원칙 |
|---|---:|---|
| 상단 | 높이 약 8% | 사건·버전·모드·동기화, 현재 요청 ID |
| 중요 변화 띠 | 높이 약 8% | 가장 중요한 미해결 상태와 전체 건수, 고정 높이 |
| 본문 | 높이 약 70% | 좌측 약 70% 지시·병렬 작업·보고 흐름 / 우측 약 30% 현재 상황·확인·대응안 |
| 하단 | 높이 약 14% | 실제 실행 시간축과 최근 핵심 변화, 표시 밀도는 실장비 검증 |

좌측의 요원 카드 세 개는 **가로로 나란히 놓고 동시에 읽는다**. 상단의 배정 카드에서 아래로 내려가는 화살표는 지시, 각 요원에서 상황실장 수신 영역으로 이어지는 화살표는 보고다. 역할별 열을 고정하고 연결선이 교차하지 않게 한다. 선에는 ‘지시’, ‘보고’를 적어 방향과 의미를 색상 없이도 이해하게 한다.

기본 화면은 스크롤·자동 페이지 전환 없이 전체 흐름과 핵심 상황을 보여준다. 제목·임무·보고는 짧게 요약하고 원문은 담당자 화면에서 연다. 한 번에 여러 요청의 연결선을 겹치지 않는다. 활성 요청을 표시하고 과거 요청은 담당자 이력에서 확인한다. 새 요청 대기는 건수로 표시한다.

### 5.1 현재 상황

가장 큰 숫자는 신고·정정 근거가 있는 총원, 구조 보고, 소재 미확인이다. 제목과 단위를 숫자와 붙여 읽게 한다. ‘구조 보고’와 ‘소재 미확인’의 의미를 줄여 ‘구조 완료’, ‘실종 확정’으로 바꾸지 않는다.

총원이 충돌하는 동안 대표 숫자 하나를 선택하지 않는다. `총원 확인 필요: 최초 신고 5명 / 명부 7명`을 같은 영역에 표시한다. 아래에는 `명부 기준: 구조 보고 4명 / 소재 미확인 3명 · 잠정`이라고 적는다.

위치는 텍스트와 제공 좌표로 표시한다. 좌표가 없으면 ‘위치 좌표 확인 필요’로 둔다. 초기에는 실제 배경지도 없이 만든 가짜 해역 지도나 임의 선박 위치를 표시하지 않는다. 지도는 위치 판단의 필요성이 확인됐을 때 실제 자료로 확장한다.

사건 전체에 근거 없는 HIGH·점수·자동 위험등급을 붙이지 않는다. ‘침수 진행 보고 / 현장 추가 보고’처럼 보고된 위험 내용을 직접 보여준다. 규칙과 확인 주체가 정해지기 전에는 AI 추정 위험도를 핵심 지표로 사용하지 않는다.

### 5.2 확인할 일과 대응안

확인할 일은 질문, 발생 이유, 해결 전 영향으로 구성한다. 기본 표시 최대 3건, 대응안은 핵심 3건을 우선 표시하고 상세 최대 5건은 담당자 화면에 둔다. 모든 미해결 건의 총수는 항상 보인다.

확인할 일이 표시 한도를 넘으면 `미해결 8건 · 이 중 우선 확인 4건 / 표시 3건`과 ‘담당자 상세 확인 필요’를 표시한다. 표시하지 못한 중요 건수가 있는 동안 정상 상태처럼 보이면 안 된다. 자동 순환 대신 담당자가 목록에서 처리한다. 긴급한 사람의 판단이 필요한 항목은 단순한 최근 시각보다 우선한다.

대응안에는 반드시 `기준 상황 S1 / 현재 S2 · 재검토 필요`처럼 적용 기준을 붙인다. 새 계획이 아직 없을 때 이전 계획을 그대로 ‘최신 대응안’이라고 표시하지 않는다. 이전안은 읽을 수 있지만 갱신 대기임을 명확히 남긴다.

AI 권고, 사람이 검토한 상태, 실제 조치가 수행됐다는 현장 보고를 서로 다른 필드로 구분한다. AI 작업이 끝났다고 현장 조치를 완료로 표시하지 않는다. 초기에는 현장 집행 관리 기능을 새로 만들지 않는다.

### 5.3 지시·병렬 작업·보고 카드

| 단계 | 기본 화면의 필수 정보 | 실제 기록과 연결 |
|---|---|---|
| 사용자 지시 | 요청 한 문장, 접수시각, 요청 ID | 사용자 메시지 |
| 상황실장 배정 | 요청 해석 요약, 선택한 요원, 임무별 배정 이유·완료 조건 | 저장된 배정 결정과 임무 |
| 요원 작업 | 받은 임무, 사용 자료·도구, 현재 단계, 시작시각·경과, 기준 버전 | 실행 시작·도구 요청·완료 이벤트 |
| 요원 보고 | 결론 한 문장, 핵심 근거, 미확인·보완 필요, 보고시각 | 저장된 보고와 근거 ID |
| 상황실장 수신 | ‘보고 2/3 수신’, 남은 보고와 종합에 필요한 조건 | 필수 보고 집합과 실제 수신 기록 |
| 종합·검증 | 종합 초안, 검증 대기 이유·결과, 보완 지시 여부 | 초안·검증 보고·보완 임무 |
| 사용자 최종 보고 | 현재 판단, 우선 대응, 확인할 사항, 근거, 이전 보고 대비 변경 | 최종 메시지·계획 버전·사용 보고 ID |

상황실장의 배정 이유는 예를 들어 ‘총원 불일치를 확인하기 위해 정보요원에게 명부 대조를 맡김’처럼 업무와 근거를 설명한다. 요원 카드에는 ‘기상 도구 응답 대기’, ‘지침 검색 완료 · 보고 작성 중’처럼 실행 이벤트로 확인되는 단계를 표시한다. 모델이 응답 중이라는 이유만으로 검색·분석 세부 단계를 임의로 생성하지 않는다.

요원이 보고하면 해당 카드에 결과가 바로 남고, 상황실장 수신 영역에 ‘정보요원 보고 수신’이 추가된다. 모든 요원이 끝날 때까지 개별 보고를 숨기지 않는다. 보고 수신은 프로그램이 접수했다는 뜻이며 상황실장의 검토·종합 완료와 구별한다.

최종 보고는 담당자 채팅과 대형 화면에 **동일한 메시지 ID**로 연결한다. 화면용 요약에서 원문을 열 수 있게 하며 별도 모델 호출로 서로 다른 최종 답을 만들지 않는다. 완료 후 카드·배정 이유·보고 요약·연결은 유지한다. 다음 요청이 시작되면 이전 실행 묶음은 이력으로 보존한다.

### 5.4 실제 병렬 실행을 눈으로 읽는 방법

독립 임무는 첫 요원의 응답을 기다리지 않고 함께 실행한다. 예를 들어 같은 상황 S0로 명부·기상 확인, 기존 지침 검색, 가상 자원표 검토를 시작할 수 있다. 최신 기상이 반드시 필요한 추가 수색 판단은 정보요원 보고 이후의 의존 임무로 둔다. 검증요원은 필요한 보고와 종합 초안이 준비된 후 검토한다.

- 실행 중인 카드들은 동시에 ‘실행 중’을 표시하고 각자의 경과시간이 진행된다. 완료한 카드는 즉시 보고 상태로 바뀐다.
- 현재 실행 수·대기 수·보고 수를 분리한다. ‘동시 실행 3건’은 실제 실행 중인 임무 수이며 배정 수가 아니다. API 한도 때문에 대기하면 ‘실행 슬롯 대기’라고 표시한다.
- 하단 시간축은 실제 시작–종료 구간을 역할별 고정 행에 표시한다. 겹친 구간으로 동시 실행을 확인하며 호출 응답 대기 시간도 실행 구간에 포함됨을 상세에 적는다.
- 화살표는 이벤트 때만 짧게 강조한다. 한 번의 화면 조회 사이에 끝난 지시·보고도 저장된 이벤트와 완료 카드로 남는다. 짧은 일을 보여주려고 완료를 늦추지 않는다.
- 순차 입력 처리와 요청 안의 병렬 실행을 구분한다. 새 사용자 입력은 즉시 접수·대기 표시하고, 현재 실행 묶음과 새 상황 버전의 결과를 섞지 않는다.

병렬 실행은 독립 작업들의 대기시간을 겹칠 수 있지만, 전체 응답속도는 배정·가장 오래 걸린 의존 경로·종합·검증·API 한도에 좌우된다. ‘몇 배 빨라짐’은 같은 입력·모델·자료로 순차/병렬 실행을 비교한 측정 이후에만 적는다. 최초 요원 보고까지의 시간과 최종 보고까지의 시간을 각각 기록한다.

필수 보고가 실패하면 ‘종합 보류 · 정보요원 재시도 필요’처럼 이유와 다음 행동을 표시한다. 확보한 결과는 중간 보고로 제공할 수 있다. 보완 한도 이후 최종 답변을 전달해야 하면 ‘일부 근거 미확보’ 또는 ‘판단 보류’를 명시하고 누락을 정상 완료로 처리하지 않는다. 상태에 변화가 없으면 같은 보고를 계속 모델에 재전달하지 않는다.

세션 생성·기억 격리·시뮬레이션 조언의 상세 계약은 [12_모델배정_시뮬레이션조언_세션기억.md](12_모델배정_시뮬레이션조언_세션기억.md)를 따른다. 상황판에 세션명을 항상 표시하고 가정 기반 결과와 현재 사실을 구별한다.

## 6. 담당자 작업 화면

같은 화면에서 **사건 확인 → 입력 → 질문 응답 → 근거 검토**가 가능하도록 구성한다.

```text
상단: 새 세션 · 세션 선택 · 상황 요약 · 동기화 상태 · [상황판 열기]
좌측 약 60%: 상황실장 대화 / 첨부 상태 / 고정 입력창
우측 약 40%: [확인할 일] [업무·근거] [대응안·이력]
```

우측 기본 탭은 ‘확인할 일’이다. 미해결 건수를 표시하고 질문을 선택하면 관련 신고·명부·집계를 함께 보여준다. 상태 변경 때문에 탭이 자동 전환되거나 입력창 포커스가 이동하면 안 된다.

- 채팅 입력은 여러 줄을 허용한다. Enter 또는 ‘전송’ 버튼으로 전송하고 Shift+Enter로 줄바꿈한다. 한글 조합 중 Enter는 전송하지 않는다. 기본 단축키는 입력창에 표시한다.
- 입력창은 작업 중에도 쓸 수 있다. 서버 저장 후에만 ‘접수됨’, 실제 처리 전에는 ‘대기 중’으로 표시한다.
- 전송 실패 시 작성 내용을 남기고 ‘재전송’을 제공한다. 재전송에는 같은 메시지 ID를 사용해 중복 접수를 막는다.
- 첨부는 파일명·형식·크기·접수/분석 상태를 보여준다. 지원 형식은 선택 전에 알린다. 초기 CSV부터 시작한다.
- 담당자가 과거 채팅을 읽고 있으면 자동으로 맨 아래로 이동하지 않는다. ‘새 메시지 2건’ 버튼으로 최신 위치에 이동한다.
- 상세는 한 번에 하나만 연다. 상세를 닫으면 이전 스크롤과 선택을 복원한다. 팝업 위에 팝업을 쌓지 않는다.
- 자주 쓰는 행동은 ‘확인 답변’, ‘근거 보기’, ‘실패 임무 재시도’, ‘기상 재조회’다. 설명을 읽지 않아도 결과를 예상할 수 있는 이름을 쓴다.

### 6.1 확인 질문에 답하는 절차

1. ‘실제 탑승 명부 확인’ 항목을 선택한다.
2. 최초 신고 5명, 명부 7명, 구조자 P01–P04, 중복·누락 검사 결과를 한 패널에서 확인한다.
3. ‘7명이 실제 승선한 명부가 맞음’, ‘명부가 다름’, ‘아직 확인하지 못함’ 중 답을 선택한다. 다른 내용은 자유문으로 적는다.
4. 적용 전 `총원 5 → 7 / 구조 보고 4 유지 / 소재 미확인 1 → 3`을 같은 패널에서 보여준다.
5. 명시적인 ‘정정 반영’ 한 번으로 답변·출처·새 버전을 저장한다. 별도 반복 확인 창은 띄우지 않는다.

알림의 ‘읽음’이나 ‘확인했다’는 조작만으로 인원 정정을 확정하지 않는다. 질문에 대한 답이 없으면 미해결로 남는다. 잘못 정정했다면 과거 기록을 삭제하지 않고 새로운 정정으로 되돌린다.

### 6.2 재시도와 중복 실행

실패한 임무에 ‘재시도’를 제공하되 현재 상황 버전을 먼저 비교한다. 버전이 같으면 실패 임무를 새 실행 ID로 재시도하고, 달라졌으면 ‘현재 상황으로 재검토’로 안내한다. 이전 지시를 최신 상황에 그대로 재실행하지 않는다.

버튼을 여러 번 눌러도 같은 실행 요청이 중복 생성되지 않게 한다. 재시도 중에는 상태를 표시하고 추가 요청을 제한한다. 전체 사건 초기화는 별도 관리 영역에 두고 진행 중 작업과 기록 보존 여부를 확인하게 한다.

## 7. 갱신·신선도·연결 규칙

아래 숫자는 **초기 프로토타입을 검증하기 위한 설정 제안**이며 현장 기준이나 제공자의 보장값이 아니다. 설정값은 한 곳에서 관리하고 실행 환경에서 조정한다.

| 구분 | 초기 제안 | 화면에 필요한 의미 |
|---|---|---|
| 화면 상태 조회 | 현재 약 1초 주기(초기 제안 2초), 저장 상태 읽기만 | 표시 갱신을 AI 호출과 분리 |
| 화면 연결 지연 | 마지막 성공 동기화 후 10초 초과 | ‘갱신 지연 · 마지막 수신 …’ |
| 화면 연결 끊김 | 마지막 성공 동기화 후 30초 초과 | ‘연결 끊김 · 이전 자료 표시 중’, 경과시간 유지 |
| 실행 작업자 상태 확인 | 5초 주기 상태 기록, 15초 이상 부재 시 이상 표시 | 서버 응답 정상과 작업 진행 정상을 별도로 판단 |
| 임무 시간제한 | 현재 모델 HTTP 요청 timeout=90초(초기 60초 후보); 전체 run 기한은 별도 미구현 | 초과 시 실패 또는 시간초과, 계속 조사 중으로 두지 않음 |
| 기상 자동 재조회 | 모니터링 활성 사건에서 30분 간격 후보 | 제공자 이용 조건·한도 검증 후 활성화, 마지막/다음 조회시각 표시 |
| 기상 수동 재조회 | 사용자 명시 요청 | 캐시/동일 요청 진행 여부 표시, 중복 요청 합치기 |

연결 지연·끊김 표시는 서버가 다시 응답해야만 나타나는 방식으로 구현하지 않는다. 브라우저에서 마지막 성공 수신 이후 경과를 감시하고, 서버가 멈춰도 경고를 표시해야 한다. 서버 응답이 없는 상태에서 이 경고가 실제로 바뀌는지 UI 후보 검증에 포함한다. 브라우저 자체가 멈추는 경우의 한계는 13절에 구분한다.

사건이 새로 없을 때의 모니터링은 DB 상태·작업 진행·연결 상태를 읽는 것으로 충분하다. 인원·침수·위치는 새로운 출처가 들어오기 전까지 변하지 않는다.

기상 자동 재조회는 화면별 타이머가 아니라 서버의 사건별 스케줄 한 개가 담당한다. 위치 변경은 기존 스케줄을 교체한다. 사건 종료 또는 담당자의 명시적인 자동 조회 중지는 스케줄을 중단한다. 상황판 창을 닫거나 표시만 중지하는 동작은 서버 스케줄을 중단하지 않는다. 첫 버전에서 자동 조회 연결이 검증되지 않았다면 명확하게 ‘수동 조회’라고 표시한다.

기상 조회 성공과 자료의 유효성은 별도다. 현재 대상시각에 해당하는 값인지 검사하고, 해당 시각 값이 없으면 ‘해당 시각 자료 없음’으로 둔다. 자료 기준시각·조회시각·예측 여부를 유지한다. 단순히 조회한 지 30분이 지났다고 위험한 기상으로 판정하지 않는다. 제공 항목별 시간 해상도와 허용 자료 나이를 연동 검증에서 결정한다.

매 상태 조회마다 AI를 실행하지 않는다. 새 신고·정정·첨부 분석 완료·사용자 재검토 요청을 임무 생성 계기로 삼는다. 정기 기상 조회만으로 무한 재지시하지 않는다. 새 근거가 현재 계획의 사용 근거를 바꾸면 ‘기상 갱신 · 재검토 필요’를 기록하고 담당자가 재검토를 요청할 수 있게 한다. 자동 재계획 정책은 후속 검증으로 둔다.

## 8. 상태는 세 종류로 나눈다

| 상태 축 | 예 | 혼동하지 않을 것 |
|---|---|---|
| 사건·자료 | 침수 진행 보고 / 총원 확인 필요 / 사용자 정정 | 앱 오류 때문에 사건 위험도가 상승하지 않음 |
| AI 업무 | 대기 / 실행 / 선행 대기 / 완료 / 실패 / 이전 버전 | AI 보고 완료가 현장 구조 완료는 아님 |
| 화면·연결 | 동기화 정상 / 지연 / 끊김 / 재연결 중 | 연결 정상이어도 기상은 오래되었을 수 있음 |

`대기`는 접수된 임무가 없는 상태, `선행 대기`는 필요한 임무가 있지만 근거를 기다리는 상태다. `이전 버전`은 보고 자체가 잘못됐다는 뜻이 아니라 최신 상황에 바로 적용할 수 없다는 뜻이다.

장애에는 항상 **상태 + 영향 + 다음 행동**을 쓴다. 예: `기상 조회 실패 — 기존 자료는 13:00 기준 — 담당자 화면에서 재조회 가능`. 화면에는 원본 스택 추적 대신 이 요약을 보여주고, 상세 진단 식별자는 담당자 영역에 둔다.

## 9. 주의 항목과 알림

| 수준 | 적용 대상 | 상시 상황판 | 담당자 동작 |
|---|---|---|---|
| 우선 확인 | 인원 불일치, 잘못된 버전 적용 차단, 주요 근거 누락으로 계획 판단 보류 | 상단 중요 띠에 유지, 영향 요약 | 질문 응답 또는 근거 보완 |
| 확인 필요 | 일부 도구 실패, 자료 갱신 지연, 미응답 질문 | 해당 카드와 확인 목록 | 재조회·재시도·확인 답변 |
| 참고 | 정상 보고 완료, 자료 접수, 일반 갱신 | 최근 변화에 짧게 기록 | 필요 시 상세 열람 |

색은 역할을 보조한다. `! 확인 필요`, `× 조회 실패`, `✓ 보고 완료`, `… 선행 대기`처럼 글자와 형태를 함께 쓴다. 같은 문제가 반복되면 건수를 무한히 늘리지 않고 동일 문제 ID에 최근 발생과 횟수를 묶는다.

알림은 `미열람 → 읽음 → 해결`을 구분한다. 읽음은 담당자가 봤다는 기록이고 해결은 정정·재조회 성공 등 원인이 실제로 해소된 상태다. 상황판 탭을 닫거나 화면을 전환해도 미해결 건은 사라지지 않는다. 문제가 해소된 뒤 다시 발생하면 새 발생으로 기록한다.

기본은 무음이다. 소리가 필요하면 담당자가 우선 확인 수준에 대해 선택적으로 켜고, 중복 경보의 재울림 간격을 설정한다. 소리를 켜지 않아도 시각적으로 모든 상태를 파악할 수 있어야 한다.

정렬은 우선도, 미해결 여부, 발생시각을 기준으로 안정적으로 유지한다. 상태 조회 때마다 행이 무작위로 이동하거나 최신 정상 로그가 미해결 확인사항을 밀어내지 않는다.

## 10. 데이터와 화면의 연결 계약

별도 대규모 플랫폼을 만들 필요는 없지만 다음 정보는 서버의 저장 상태로 설명할 수 있어야 한다.

| 표시 요소 | 근거가 되는 저장 정보 | 갱신 조건 |
|---|---|---|
| 현재 인원·출처 | Incident.version, claims, 집계 범위, 확인 상태 | 검증된 상황 갱신 거래 완료 |
| 요원 상태·경과 | Task.task_id, run_id, based_on_version, status, started_at, completed_at | 실제 작업 이벤트 |
| 지시부터 최종 보고 | 사용자 message_id, run_id, 배정 요약·이유, depends_on, report_id, 최종 메시지의 사용 보고 ID | 실제 접수·배정·실행·수신·종합·최종 전달 이벤트 |
| 최신안·재검토 | Plan.plan_id, based_on_version, review_status, evidence_ids | 계획 저장 또는 사용 근거 변경 |
| 미해결 질문 | 질문 ID, 관련 주장/자료, 열린 시각, 해결 조건, 상태 | 질문 생성·응답 적용 |
| 알림 읽음 | 문제 ID, 읽은 시각, 발생·해결 상태 | 담당자의 명시 동작 또는 원인 해소 |
| 기상 신선도 | 항목별 valid_at, retrieved_at, 단위, 좌표, source_ref | 실제 도구 결과 저장 |
| 화면 최신성 | 화면이 마지막으로 성공 수신한 시각, snapshot_revision | 조회 성공, 재연결 |
| 연결·작업자 상태 | transport 상태, 작업자 heartbeat, 시간초과 | 관측된 통신·실행 상태 |

하나의 사용자 요청 처리를 run_id로 묶고, 재시도·보완은 해당 묶음 안에 고유 실행 ID로 남긴다. 최종 메시지에서 사용한 보고와 배정 이유까지 역으로 연결할 수 있어야 한다. 이벤트 순번으로 누락·중복 표시를 방지한다.

질문·알림 등은 기존 Event와 구조화 필드로 시작할 수 있다. 위 표의 행마다 독립 테이블을 만들라는 요구가 아니다.

**한 번의 읽기에서 일관된 화면 스냅샷을 만든다.** 인원은 S2인데 근거는 S0, 대응안 상태는 S1 완료인 내용을 설명 없이 섞지 않는다. 대응안이 아직 S1이면 그 차이를 화면의 상태로 드러낸다.

상황 버전은 사건 의미가 바뀔 때 갱신하고, `snapshot_revision`은 작업·알림 변화도 포함한 표시용 순서다. 두 화면은 같은 저장 상태를 읽지만 조회 시점은 다를 수 있다. 버전과 최종 동기화 시각을 표시하고 목표 2초 이내 차이를 시험한다. 시간순 정렬은 서버의 이벤트 순번을 우선하며 브라우저 시계 오차로 기록 순서가 바뀌지 않게 한다.

## 11. 실행 구조와 기술 선택

```text
담당자 입력 → 서버 접수·저장 → 사건별 작업 큐 → 상황실장·요원·도구
                     ↑                         ↓
                     └──── 검사·버전·결과 저장 ──┘
                                     ↓
                         일관된 화면 스냅샷
                           ↙               ↘
                  담당자 작업 화면     읽기 전용 상황판
```

화면은 업무 실행자가 아니라 입력 창구와 저장 상태의 관찰자다. 브라우저를 두 개 열어도 외부 기상 요청이나 요원 임무가 두 번 실행되지 않아야 한다. 담당자 화면을 닫아도 서버가 실행 중이면 이미 접수된 임무는 계속 처리한다. 서버가 종료되면 진행 중 임무는 재시작 시 ‘중단됨/재검토 필요’로 복구하며 조용히 완료로 만들지 않는다.

### 11.1 현재 후보를 검증하는 순서

현재 Python HTTP·SQLite·서버 작업 큐와 HTML/CSS/JavaScript를 채택했다. 아래는 현재 UI에서도 적용할 수용 기준이며, Streamlit 관련 설명은 과거 후보 검토 기록이다.

1. 담당자 탭과 상황판 탭을 열고 동일 사건 스냅샷을 읽는다.
2. 현재 약 1초 갱신 중에도 작성 중인 글·한글 조합·선택·스크롤이 유지되는지 확인한다.
3. 한 번 전송했을 때 작업 생성과 모델 호출이 각 한 번인지 확인한다.
4. 한 탭을 닫아도 다른 탭과 작업자가 계속 동작하는지 확인한다.
5. 서버 중단·재시작, 연결 지연, 이전 버전 보고를 화면에서 구분한다.

Streamlit 공식 문서는 `st.fragment(run_every=...)`의 부분 재실행을 설명한다. 세션 상태는 사용자 세션에 묶이므로 두 창의 공통 사건 상태를 브라우저 세션만으로 관리하지 않는다. DB에 저장하고 각 창이 읽어야 한다. 이 공식 기능 설명만으로 위 실험을 통과했다고 간주하지 않는다. [부분 재실행 문서](https://docs.streamlit.io/develop/api-reference/execution-flow/st.fragment), [세션 상태 문서](https://docs.streamlit.io/develop/concepts/architecture/session-state).

부분 갱신·지속 입력·두 화면 동기화를 안정적으로 만족시키지 못하면, Python 실행부와 DB는 유지하고 상태를 읽는 얇은 HTTP 인터페이스 및 별도 웹 UI를 대안으로 검토한다. 구체적인 프런트엔드 프레임워크는 이 문서에서 확정하지 않는다.

### 11.2 읽기와 쓰기의 분리

상황판 갱신은 DB 조회이며 모델·외부 API 호출을 유발하지 않는다. 큐 처리와 기상 스케줄은 서버의 단일 조정자가 맡는다. 단일 조정자는 순차 요원 실행을 의미하지 않는다. 준비된 독립 임무를 제한된 동시 실행 슬롯에 넘기고, 선행 결과가 필요한 임무는 대기시킨다. SQLite 쓰기는 짧은 거래로 처리하며 모델 응답을 기다리는 동안 DB 쓰기 잠금을 잡지 않는다. UI 재실행 때 작업 스레드를 매번 생성하지 않는다. DB 갱신은 거래로 수행하고 충돌한 정정은 새 현재값을 보여주며 다시 검토하게 한다.

첫 버전은 단일 서버·단일 입력 담당자면 충분하다. Redis, 분산 큐, 별도 벡터 서버를 상시 화면이라는 이유만으로 도입하지 않는다.

## 12. 글자·색·밀도·움직임

| 항목 | 초기 제안 | 검증 방법 |
|---|---|---|
| 중요 인원 | 64–80 CSS px | 실제 대형 모니터의 예상 최장 시청 거리에서 읽기 |
| 영역 제목·핵심 변화 | 28–36 px | 문장 1–2줄로 의미 파악 |
| 본문·임무 요약 | 24–28 px | 한 카드 3개 핵심 항목 이내 |
| 시각·출처 보조정보 | 20–22 px | 출처 구분과 오래된 자료를 멀리서 읽기 |
| 담당자 화면 본문 | 16–18 px | 입력·표·상세 근거의 읽기 편의 |
| 배경·표면 | 짙은 남색과 불투명 패널 | 반사·조명·장비 밝기에서 확인 |
| 강조 | 청록: 진행, 주황: 확인 필요, 빨강: 실패, 중립: 대기 | 색을 제거해도 텍스트로 상태 구분 |

이 크기는 표준의 강제값이 아니라 시작값이다. 55–65인치·약 3–5m를 첫 검토 가정으로 삼되 실제 장비와 거리로 결정한다. 전체 화면을 CSS scale로 작게 만들어 무조건 맞추지 않는다. 정보량을 줄이고 중요한 글자 크기를 보존한다.

텍스트 대비는 일반 글자 최소 4.5:1, 큰 글자 최소 3:1을 기준으로 점검한다. 큰 글자의 해당 여부는 W3C 정의를 따르고, 실제 투사·반사 환경의 가독성은 별도 시험한다. [W3C 대비 설명](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html).

정보를 새로 표시할 때 포커스를 빼앗지 않고, 중요한 상태 변경을 보조기술이 인식할 수 있게 한다. 모든 타이머·하트비트를 음성으로 읽지 않고 접수·실패·확인 필요 같은 의미 있는 변경만 알린다. [W3C 상태 메시지 설명](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html).

운영 화면에서는 자동 카메라 회전·3D 패널 분해·배경 입자·자동 스크롤·긴 타자 효과를 사용하지 않는다. 최신 사용자 요구로 실제 진행 중 카드의 밝은 글로우를 적용한다. 완료 뒤에는 안정된 표시로 돌아가고 임무 상태를 과장하지 않는다. 새 값이 들어오면 해당 항목의 배경을 짧게 강조하고 안정된 상태로 돌아온다. 변경 전후 값과 시각은 효과가 끝난 후에도 이력에 남는다. 동작 줄이기 설정에서는 강조 애니메이션 없이 문구·표식으로 알린다.

## 13. 시작·무사건·종료·재접속

| 상황 | 보여줄 것 | 사용자 행동 |
|---|---|---|

빈 화면을 가상 사건·기상값으로 채우지 않는다. 종료 후 늦게 도착한 결과는 이력에 보존하되 종료된 사건의 활성 계획으로 자동 반영하지 않는다. 사건 종료는 사람이 명시하며 요원 작업 완료로 자동 종료하지 않는다.

브라우저·OS가 완전히 정지하면 내부 자바스크립트만으로 화면에 장애를 표시할 수 없다. 초기 검증에는 화면 절전·전체화면 유지·운영자의 시계 확인을 포함한다. 별도 외부 감시·키오스크 복구·24시간 운영 체계는 후속 운영 설계로 남긴다.

## 14. 실제 사용 시나리오로 검증하기

### A. 평상시 상시 표시

담당자 화면을 조작하지 않아도 사건·자료·작업 상태가 갱신된다. 갱신할 자료가 없으면 값은 그대로이고 연결 시각만 바뀐다. 30분 동안 새 입력이 없다고 모델을 반복 호출하지 않는다.

### B. 명부 불일치와 정정

S0에서 5/4/1을 표시한다. S1 명부 업로드 후에는 5와 7의 출처를 병기하고 확인할 일을 만든다. S2 사용자 답변을 적용하면 7/4/3, 출처 ‘사용자 정정’, 새 상황 버전을 함께 보여준다. 기존 대응안에는 재검토 필요가 붙고, 새 임무·검증이 끝나야 새 계획이 나타난다.

### C. 기상 실패

기상 도구가 실패하면 기상 카드와 확인 목록에 실패를 표시한다. 이전 값이 있다면 조회 당시 값·기준시각을 보존하되 현재값인 것처럼 표시하지 않는다. 이전 값도 없으면 숫자 대신 ‘미확인’을 사용한다. 나머지 업무는 가능한 범위에서 진행하며 계획에는 누락 근거를 남긴다.

### D. 늦은 보고와 복원

S1 작업 중 S2가 접수되면 S1 결과는 ‘이전 상황 기준’으로 보존한다. 재시작 후 진행 중 표시를 무기한 유지하지 않고 실행 ID·작업자 상태를 대조한다. 두 창이 같은 최신 버전을 회복해야 한다.

### E. 담당자 교대

새 담당자는 사건 요약, 미해결 확인사항, 최근 중요 변화, 대응안 기준 버전을 먼저 본다. 필요하면 기록된 원문으로 들어간다. 교대 요약을 보기 위해 전체 대화를 처음부터 읽거나 별도 AI 요약 호출이 반드시 필요하게 만들지 않는다.

## 15. 개발 순서와 완료 기준

기존 P0–P7을 유지하면서 모니터링을 각 단계에 붙인다. 모든 요원을 구현한 뒤 처음 상황판을 만드는 순서로 미루지 않는다.

| 단계 | 추가할 최소 흐름 | 완료 증거 |
|---|---|---|
| P0 | 접수·응답 저장 + 같은 사건을 읽는 상황판 | 두 창에서 동일 입력·버전 확인, 입력 내용 유지 |
| P1 | 실제 임무 상태·보고 + 새 입력 대기열 | 지시·보고 연결, 대기·실패 구분, 중복 호출 없음 |
| P2 | 기상 조회·자료시각·실패·재조회 | 실제 응답과 표시 일치, 조회와 화면 갱신 분리 |

## 17. 시상 전략과 연결

대형 화면에서 ‘무엇이 바뀌고, 무엇을 확인하며, 어떤 임무와 계획이 갱신됐는지’를 읽게 하는 것은 06번 문서의 업무 적용·신뢰성·시연 가독성 전략을 구체화한다.

발표에서는 담당자 화면에 명부를 넣고 대형 상황판에 불일치가 나타나는 장면, 확인 답변 후 상황·임무·계획 상태가 연결되어 바뀌는 장면을 우선한다. 기상 장애 시 ‘미확인’이 명확하게 남는 모습도 실제 검증 증거로 쓸 수 있다.

상시 상황판이 있다는 것만으로 공식 배점 우위나 수상을 보장하지 않는다. 가치 주장은 구현된 기능과 시험 기록으로 뒷받침한다. 발표용 3D 자료와 운영 화면은 같은 사실·상태 의미를 사용하되, 표시 효과와 정보 밀도는 각 목적에 맞춘다.

## 19. 최신 모니터링 반영과 미완료 항목

현재 상태 조회는 약 1초이며 기존 2초는 초기 목표였다. 접수 즉시 피드백, 상단 ‘지시 수행 중’, 배정·요원 검토·보고·종합 상태, 실제 실행 시간축, 핵심 제안·정보요구 각각 앞 2건과 펼침을 구현했다. 모델명·추론 수준을 숨기고 Enter 전송·Shift+Enter 줄바꿈, 세션 삭제, 대형화면 복귀 링크를 제공한다.

‘전체의 생각’을 본다는 것은 요청·배정 이유·임무·보고·근거·확인할 정보의 흐름을 파악한다는 뜻이다. 첫 호출 안의 토큰 스트리밍·실제 사고 단계는 제공하지 않는다. 진행 문구는 서버가 아는 실행 상태까지만 설명한다.

질문 ID별 해결·알림 읽음·작업자 heartbeat·자동 기상 감시·사건 종료·복구 후 변경 건수는 위 설계 목표이며 현재 구현된 일반 이벤트 목록과 다르다. 세션 삭제는 보관/종료가 아니며 queued/running 작업이 있으면 거절한다. 화면의 숨김·고정은 권한 체계가 아니다.

실제 장비·거리 가독성, 모든 제안 길이에서 요원 영역 유지, 최신 삭제/복귀 동선, 동작 줄이기 설정, 2시간 연속 시험은 미완료다. 현재 코드·검증 범위는 13번 문서를 따른다.
