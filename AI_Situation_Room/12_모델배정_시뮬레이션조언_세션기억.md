## 1. 역할별 모델 설정

| 역할 | 모델 | 추론 수준 | 적용 업무 |
|---|---|---|---|
| 상황실장 | GPT-6 Luna (`gpt-6-luna`) | `medium` | 요청 해석, 배정, 종합, 대안 비교, 사용자 조언 |
| 정보요원 | GPT-6 Luna | `medium` | 자료·명부·기상 검토 및 보고 |
| 수색구조요원 | GPT-6 Luna | `medium` | 지침 검색·대응 검토 및 보고 |
| 자원지원요원 | GPT-6 Luna | `medium` | 등록 세력·사용자 보고 상태·제약 검토 및 보고 |
| 검증요원 | GPT-6 Luna | `medium` | 근거·모순·가정·계획 검증 |

사용자가 지정한 ‘Luna’를 현재 모델명 GPT-6 Luna로 해석했다. 모든 역할은 `medium` 추론 수준을 사용한다. 모델과 역할별 추론 수준을 중앙 설정 한 곳에서 관리하고, 실제 호출마다 적용값을 기록한다. 재시도·보완·시뮬레이션에서도 동일 역할의 설정을 유지한다. 임의의 다른 모델로 자동 대체하지 않는다. 연결 실패 시 실패와 원인을 표시한다.

프로젝트는 Responses API의 reasoning.effort에 medium을 전달한다. 요청 형식 단위 시험과 과거 LIVE 호출 기록이 근거이며, 현재 설정의 새 전체 LIVE 시험은 미실시다. 기존 문서의 [모델 참고 링크](https://developers.openai.com/api/docs/models/gpt-6-luna)는 보존하되 이번 현행화에서 외부 명세를 재검증하지 않았다. 모델 주도 도구 호출도 아직 구현하지 않았다.

이 설정은 앱 내부 요원 구성이다. 현재 Codex 대화의 모델을 바꾸는 작업이 아니다. 동일 모델을 여러 역할로 사용하는 것은 서로 다른 모델 비교 실적이 아니며 교육용 멀티모델 비교는 별도 실험이다.

## 2. 상황실장은 조언까지 담당한다

사용자는 ‘현재 상황에서 어떤 선택이 나은가’, ‘조건이 달라지면 판단이 어떻게 바뀌나’처럼 질문할 수 있다. 상황실장은 세션에 저장된 사실·요원 보고·이전 시뮬레이션을 확인하고, 부족한 검토가 있으면 필요한 요원에게 맡긴다.

조언은 다음 순서로 전달한다.

1. **권고 요약:** 지금 자료로 제안할 수 있는 선택 또는 판단 보류.
2. **근거:** 기준 상황 버전, 사용 보고·지침·기상 등 출처.
3. **비교:** 검토한 대안별 기대효과·제약·불확실성.
4. **성립 조건:** 어떤 가정에서 이 권고가 유효한가.
5. **다음 확인:** 무엇을 추가로 알아야 판단이 달라질 수 있는가.

적합한 기존 시뮬레이션이 있으면 기준 상황·가정·자료 유효성을 확인해 재사용하고 실행 ID를 인용한다. 관련 조건이 바뀌었거나 비교가 없으면 새 시뮬레이션을 수행한다. 단순 결과 설명에는 불필요한 새 작업을 만들지 않는다. 결과가 없거나 실패했으면 ‘시뮬레이션 검토 전/실패’라고 밝히며, 일반 설명을 실행된 결과인 것처럼 말하지 않는다.

## 3. 시뮬레이션의 의미와 실행 흐름

초기 구현은 **조건을 바꿔 대응 대안을 비교하는 가정 기반 시나리오 검토**다. 실제 요원 호출과 자료 검토를 실행하지만, 물리 모델 기반 표류·구조 성공률 예측을 구현했다는 뜻은 아니다. 가상 자원표를 사용한 비교는 결과에도 표시한다.

```text
사용자 질문 + 해당 세션의 현재 상황
              ↓
상황실장: 비교 목표·기준 버전·가정·대안 구성
              ↓
필요한 요원의 독립 검토 병렬 실행
              ↓
요원별 보고 → 검증요원 → 상황실장 최종 종합 (현재 실행 순서)
              ↓
조건부 조언 + 근거 + 미확인사항 → 같은 세션에 저장
```

- 처음에는 기준안과 대안 1개를 비교하는 작은 흐름부터 구현한다. 대안 수 확장은 실행 비용·응답시간을 확인한 뒤 한다.
- 공통 기준 상황과 제약을 각 요원에게 전달하며, 대안마다 변경한 조건을 명시한다.
- 지침·출처가 뒷받침하지 않는 확률·도착시간·피해 수치를 만들지 않는다. 입력과 계산식이 확보된 항목만 코드로 계산하고, 나머지는 정성 비교 또는 판단 보류로 표시한다.
- 필수 정보가 부족하면 사용자에게 확인하거나 명시적인 가정으로 검토한다. 의사결정을 바꿀 핵심 가정을 조용히 확정하지 않는다.
- 임무의 범위·시간제한·보완 횟수는 기존 실행 규칙을 따른다. 자동 무한 시뮬레이션은 하지 않는다.

### 가정과 현재 사실의 분리

각 실행은 `simulation_id`와 `base_incident_version`을 가진다. 가정 변경은 해당 시뮬레이션 안에만 저장하고 사건의 실제 인원·기상·자원 상태를 덮어쓰지 않는다. AI 예상 결과를 새 현장 보고로 저장하지 않는다.

예를 들어 사용자가 ‘자원 하나를 사용할 수 없다고 가정하면 대안이 어떻게 달라지나’라고 묻는 경우, 현재 자원표는 유지하고 ‘자원 사용 불가’ 가정의 대안을 별도로 검토한다. 결과는 가능 조건과 추가 확인사항을 설명하며 실제 자원 배치·출동을 실행하지 않는다.

사용자가 비교안을 계획 초안으로 채택해도 ‘가정 기반 초안’으로 기록한다. 가정을 실제 사실로 확정하려면 별도의 사용자 정정·출처 확인 절차가 필요하다. 계산 도중 관련 상황이 바뀌면 ‘이전 상황 기준’으로 남기고 재검토를 안내한다.

## 4. 세션은 독립된 사건 작업 공간

하나의 세션은 하나의 사건·훈련과 그 대화·자료·기억을 담는다. 사용자는 여러 세션을 만들고 이름을 붙여 전환·재개할 수 있다. 새 세션은 비어 있는 기억으로 시작한다. 세션 복제·교차 사건 검색·자동 기억 공유는 초기 범위에 넣지 않는다.

| 세션 안에 보존할 기억 | 공유 가능 범위 |
|---|---|
| 대화 원문·첨부·사건 상황·정정·사용자 결정 | 해당 세션만 |
| 요원 임무·보고·근거·대응안·알림 | 해당 세션만 |
| 시뮬레이션 가정·결과·조언·후속 질문 | 해당 세션 및 해당 시뮬레이션 |
| 긴 대화 요약·미해결사항·기억 적용 범위 | 해당 세션만 |
| 역할 지침·모델 설정·공통 공개 매뉴얼 | 공통 설정·명시된 공용 자료 |

‘A호 사건’과 ‘B호 사건’에 서로 다른 인원이 있으면, 이름이 비슷하거나 질문 문장이 같아도 답변과 검색 근거가 섞이지 않아야 한다. 모델은 이전 호출 내용을 자동으로 정확히 기억한다고 가정하지 않는다. 서버가 세션 저장소에서 필요한 기억을 읽어 매 호출의 입력을 구성한다.

긴 대화는 최근 원문 + 출처가 연결된 요약 + 현재 구조화 상태 + 필요한 과거 근거로 구성한다. 요약에는 적용한 메시지 범위와 버전을 기록하고, 정정된 값·미해결 모순을 보존한다. 요약이 원본 기록을 대체하거나 가정을 사실로 승격하지 않도록 검사한다.

## 5. 저장·검색·실행의 격리

세션은 브라우저 탭이나 LLM API의 대화 ID와 다른 제품 데이터다. SQLite에 영속 저장하고 창을 닫거나 앱을 재시작해도 복원한다. 첫 구현은 세션 1개에 사건 1개를 연결하고 기존 `incident_id`를 유지한다.

| 항목 | 추가 계약 |
|---|---|
| Session | session_id, title, incident_id, status, created_at, updated_at |
| 실행·대화·임무·보고·이벤트 | session_id, run_id, 상황 버전; 시뮬레이션이면 simulation_id도 포함 |
| Simulation | simulation_id, session_id, base_incident_version, assumptions, alternatives, evidence_ids, report_ids, status |
| Advice | advice_id, session_id, source_run_id, simulation_ids, basis_version, recommendation, limitations |
| MemorySummary | session_id, covered_message_range, summary_version, source_refs, unresolved_items |
| 실제 모델 호출 기록 | 역할, session_id, run_id, 요청 모델, 추론 수준, 반환 모델·usage(제공 시), 상태 |

필드마다 새 테이블을 만들라는 요구가 아니다. 핵심은 소속과 참조 무결성이다.

- 저장·조회·임무 배정·결과 반영에는 `session_id`를 필수로 받는다. 누락 시 전체 데이터 조회로 대체하지 않는다.
- 서버가 임무·보고·첨부·근거의 세션 소속을 검사한다. 프롬프트의 ‘다른 세션을 보지 말라’는 문구만으로 격리하지 않는다.
- 벡터 검색도 해당 세션의 문서와 명시적인 공용 자료로 검색 범위를 제한한다. 검색 후 프롬프트에서 제외하는 방식만 사용하지 않는다.
- 대화·조언·검색 결과 캐시는 세션과 상황 버전·자료 범위를 포함한다. 원시 공개 기상 응답 캐시는 요청 조건이 동일하면 공유할 수 있으나 사건 해석·위치 선택·결과 연결은 세션별로 한다.
- API 대화 연결 ID를 사용한다면 세션·역할·실행/시뮬레이션 소속을 함께 기록한다. 전역의 마지막 응답 ID를 다음 세션에 재사용하지 않는다.
- 새 세션으로 이동해도 기존 작업은 원래 세션에 완료된다. 콜백은 현재 선택된 UI 세션이 아니라 작업 생성 시 저장된 세션으로 결과를 보낸다.
- 세션별 입력 대기열을 두고 전체 호출 슬롯에 공정하게 배분한다. 한 세션 안의 독립 임무 병렬 실행과 여러 세션의 작업을 같은 전역 호출 한도 안에서 조정한다.

세션 여러 개를 지원하는 것과 다중 사용자 인증·권한 체계는 별개다. 초기에는 한 명의 담당자가 여러 세션을 사용하는 범위를 유지한다.

## 6. 실제 화면에서의 사용

담당자 화면에는 ‘새 세션’, 세션 목록, 현재 세션명·ID, 작업 중/확인 필요 건수를 제공한다. 세션을 전환하면 대화·자료·상황·조언·시뮬레이션·작성 중 입력도 각각의 세션 것으로 바뀐다. 전환 시 입력 초안을 섞거나 잃지 않는다.

질문은 상황실장 채팅에서 그대로 입력한다. 조건 비교가 필요하면 채팅 안에 ‘시나리오 검토’ 카드를 만들어 기준 버전·가정·비교안·요원 진행을 표시한다. 최종 조언에는 ‘왜 이 선택인가’와 ‘어떤 조건이면 달라지나’를 함께 보여준다.

대형 상황판은 `표시 세션`을 고정한다. 담당자가 다른 세션을 열어도 모니터가 자동으로 따라 바뀌지 않는다. ‘이 세션을 상황판에 표시’를 누를 때만 변경한다. 화면 상단에 세션명·사건 ID를 항상 표시한다. 여러 세션을 한 화면에 합치는 통합 관제는 후속 범위다.

시뮬레이션 진행은 현재 사실과 별도 배지·영역에 표시한다. 대안 카드 선택으로 상황판의 사실 숫자가 바뀌면 안 된다. 다른 세션의 완료는 세션 목록의 배지로 알리고 현재 채팅에 보고를 삽입하지 않는다.

세션 목록에서 숨기는 행위와 사건 종료를 구분한다. 종료는 기존 작업·스케줄 중단 및 늦은 결과 보존 규칙을 따른다. 한 세션 종료가 다른 세션 작업을 취소하지 않는다.

## 7. 구현 순서와 수용 기준

| 단계 | 먼저 완성할 흐름 | 확인할 결과 |
|---|---|---|
| P0 | 세션 생성·선택·저장, 상황실장 Luna Medium 호출 | 두 세션 대화 격리, 재시작 복원, 실제 모델 설정 기록 |
| P1 | 요원 Luna Medium, 세션별 큐와 보고 | 세션 전환 중 늦은 보고가 원래 세션으로 복귀 |
| P2–P5 | 기존 기상·명부·RAG·검증에 세션 소속 적용 | 다른 세션 근거 검색·참조 차단, 공용 매뉴얼만 명시 공유 |
| P5 이후 작은 추가 흐름 | 기준안+대안 1개 시나리오 검토 → 근거 있는 조언 | 실제 요원 보고 연결, 가정/사실 분리, 실패 시 결과 위조 없음 |
| P6–P7 | 두 화면 고정 세션·복구·격리·비용 검증 | 아래 사례 실행 기록 |

필수 사례:

1. A세션에 ‘총원 5명’, B세션에 ‘총원 9명’을 저장하고 번갈아 질문해 각 세션의 출처와 수치를 확인한다.
2. A만 명부를 첨부하고 B에서 같은 내용을 검색해 A의 문서·요약·조언이 반환되지 않는지 확인한다. 잘못된 세션의 report_id 직접 참조도 거절해야 한다.
3. A 임무 실행 중 B로 전환한다. 완료 보고는 A에만 기록되며 B의 화면·메모리를 바꾸지 않아야 한다.
4. 상황판은 A 고정, 담당자 화면은 B로 두고 각 세션 내용·표시 ID·입력 초안을 확인한다.
5. A의 시뮬레이션에서만 인원 또는 자원 가정을 바꿔 A의 사실과 B의 모든 데이터가 유지되는지 확인한다.
6. 저장된 시뮬레이션에 대해 후속 질문한다. 유효하면 근거로 재사용하고, 관련 상황 정정 후에는 이전 버전임을 표시한다.
7. 새 세션은 기존 대화 없이 시작하고 재시작 후 기존 세션들은 각각 복원되는지 확인한다. 대화 요약 이후에도 정정·출처·불일치가 유지되어야 한다.
8. 실제 요청 기록에서 상황실장 포함 모든 역할 medium을 확인한다. 설정 표시만 바뀌고 실제 요청이 달라지지 않는 문제를 검사한다.

## 8. 결정의 근거와 현재 상태

모델 추론 수준, 시뮬레이션 기반 조언, 여러 세션과 독립 기억은 최신 사용자 요구다. GPT-6 Luna 매핑, 초기 기준안+대안 1개, 세션당 사건 1개, 영속 저장·격리 방식은 이를 구체화한 설계다.

이 문서는 실제 설정 적용·시뮬레이션 실행·세션 격리 시험 완료 보고가 아니다. 이후 세션 격리와 가정 비교 흐름의 부분 프로토타입을 구현했으며, 실제 진행 상태와 미검증 범위는 04번 문서 및 prototype/PROGRESS.md에서 관리한다.


## 9. 실제 구현과 남은 설계의 구분

현재 `gpt-6-luna`와 전 역할 `medium`은 models.py의 실제 요청 설정이다. 화면에는 모델명·추론 수준을 표시하지 않는다. 과거 high 시험 기록은 당시 값 그대로 남기며 현재 설정의 실증 결과로 재사용하지 않는다.

세션 생성·전환·영속 저장·후속 기억·첨부 격리·고정 상황판과 조건 비교는 구현됐다. 세션 목록 ×는 확인 후 해당 세션의 기록을 삭제하고 고정 설정도 지운다. queued/running 실행 중에는 거절한다. 복제·보관·사건 종료·권한 관리는 미구현이다.

§4의 자동 긴 대화 요약·미해결 추적, §5의 독립 Simulation/Advice/MemorySummary 객체, §6의 세션별 미열람 완료 배지와 전용 시나리오 카드·종료 흐름은 목표다. 실제 저장은 세션 장부와 objects 테이블의 runs/tasks/messages/events/attachments/calls이며 시뮬레이션은 run.kind·assumptions·based_on_version으로 구분한다.

현재 상황실장 plan은 갱신안과 배정을 함께 반환한다. 최신 사용자의 ‘짧게 해석 후 곧바로 요원 배정’은 프롬프트·UI에 반영됐지만 실행 책임 분리까지 끝난 것은 아니다. 자동 과거 시뮬레이션 탐색·재사용이나 검증된 물리 예측은 구현하지 않았다. 13번 문서에 세부 코드 경로와 다음 검증을 기록한다.
