## 1. 제품 정의

사용자가 상황실장 AI와 채팅으로 사건 정보와 자료를 제공하면, 상황실장이 필요한 전문요원에게 조사·검토를 지시하고 보고를 종합해 현재 상황과 대응계획을 갱신하는 의사결정 지원 시스템이다.

핵심 메시지는 **AI Assistant에서 AI Organization으로**다. 사건에 관한 사실·근거·불확실성과 업무의 진행 과정을 사용자가 함께 확인한다. 해양사고를 첫 시연 사례로 삼되 정보요원 등 역할 이름은 범용적으로 유지한다. 다른 분야 적용은 자료·도구·검증 기준을 바꿔야 한다.

## 2. 해결할 문제와 시연 목표

- 신고·명부·기상·매뉴얼이 나뉘어 있어 공통 상황 정리가 필요하다.
- 업무마다 필요한 자료와 검토 기준이 다르다.
- 추가 보고가 기존 인원·계획과 충돌할 때 원본과 변경 이유가 남아야 한다.
- 사용자가 AI의 지시, 조사, 보고, 검증 과정을 이해할 수 있어야 한다.

핵심 시연은 **채팅 접수 → 필요한 임무 배분 → 근거 조사·보고 → 종합·검증 → 추가 자료 → 불일치 확인·재지시 → 수정안과 이력**이다. 모든 입력에 모든 요원을 호출하지 않는다.

## 3. 역할과 책임

| 역할 | 책임 | 주요 자료·도구 |
|---|---|---|
| 상황실장 | 사용자 소통·시뮬레이션 기반 조언, 상황 갱신안, 임무 선택·지시, 종합·수정 | 사건 요약·보고·자료 참조 |
| 정보요원 | 선박 제공자료·명부 대조, 기상 조회, 사실관계·누락 확인 | 파일 분석, 기상 도구 |
| 수색구조요원 | 지침 근거와 위험·구조 검토사항 제시 | 현재 공통 매뉴얼·단어 검색, 벡터 RAG는 목표 |
| 자원지원요원 | 필요한 세력·제약·추가 확인 검토 | 사용자 제공 동해 세력 카탈로그; 실시간 가용성 미연동 |
| 검증요원 | 인원 모순, 근거 누락, 사실·추정 혼동, 계획 간 충돌 점검 | 상황·보고·계획·근거 |

상황실장은 의미를 판단하고, 프로그램은 지시 형식·버전·합계를 검사해 실행·저장한다. 별도 DB 관리요원이나 무제한 요원 간 대화는 만들지 않는다.

## 4. 목표 범위

| 구분 | 포함 기능 |
|---|---|
| 세션·기억 | 여러 세션 생성·전환·재개, 세션별 대화·자료·상황·보고·조언 격리. [12_모델배정_시뮬레이션조언_세션기억.md](12_모델배정_시뮬레이션조언_세션기억.md) 참조 |
| 조언 | 해당 세션의 근거와 가정 기반 시나리오 비교에 따른 조건부 권고 |
| 사용자 참여 | 지속 채팅, 지원 형식의 자료 첨부, 정정과 확인 답변 |
| 조직 실행 | 실제 상황실장·요원 호출, 배정 이유·지시, 독립 임무 병렬 실행, 개별 보고·종합·사용자 최종 보고 |
| 자료 활용 | 가상 CSV 명부 전체 대조, 제공된 선박자료, 소규모 지침 검색 |
| 외부 데이터 | 무료 범위의 기상·해상 API만. 정보요원이 조회 |
| 교육 적용 | Agent, 벡터 검색 RAG, 실제 MCP 도구 연계, 동일 조건 멀티모델 비교, 신뢰성 검증 |
| 기록 | 상황·임무·대화·첨부·기상·대응안 이력과 복원 |
| 시각화 | 상황실장 채팅, 방향 화살표·대화 상세, 현재 상황판, 변경·근거·검증 표시 |
| 상시 모니터링 | 같은 사건을 읽는 두 화면에서 지시→배정→병렬 작업→개별/최종 보고를 가시화하고, 현재 상황·갱신·연결·확인사항을 함께 감시. 상세는 [11_상시모니터링_UIUX_설계.md](11_상시모니터링_UIUX_설계.md) |

멀티모델 비교는 별도 동일 조건 실험으로 준비할 수 있다. 운영 중 모든 역할에 다른 모델을 쓸 필요는 없다. 목표 범위를 구현 완료로 해석하지 않는다.

## 5. 제외·후속 범위

- 선박·MMSI·AIS API, 실제 내부망·함정 DB 연동
- 실제 출동명령·외부기관 메시지 자동 발송
- 정밀 표류 예측·자동 수색구역 산정·항공 운용 적합성 자동 판정
- 모든 문서 형식과 복잡한 도면 자동 이해, 음성·무전 연계
- 다중 사용자·권한 체계·분산 DB·범용 프레임워크 구축
- 별도 기상요원·DB요원 추가

도면 업로드와 이해는 별개다. 초기에는 설명 텍스트가 있는 제공자료를 쓰고 OCR·복잡한 도면 해석은 후속 검증 대상으로 둔다.

## 6. 기본 구현안과 확정 여부

| 영역 | 기본 구현안 | 결정 조건 |
|---|---|---|
| UI | HTML·CSS·JavaScript 담당자 화면 및 고정 상황판 | 현재 구현. Streamlit은 초기 후보였음. 최신 브라우저·원거리 시험 필요 |
| 실행 | Python의 작은 dispatcher·작업 큐 | 독립 임무 병렬, 의존 임무 순차 |
| 일반 DB | SQLite | 상황 버전·원본·결과 보존 |
| 벡터DB | 로컬 Chroma PersistentClient | 교육 플랫폼 검색 제공 시 연계 가능성 검토 |
| 임베딩 | 한국어 검색을 검증한 로컬 모델 후보 | 다운로드·속도·검색 품질 사전 확인 |
| 기상 | Open-Meteo 우선 후보 | 해상 좌표·항목·응답·이용 조건 실제 테스트 필요 |
| MCP | 기상 조회 도구 1개 | 실제 MCP 요청·응답 경로 확인 |
| LLM | GPT-6 Luna: 전 역할 medium | 실제 호출 이력 있음. 최신 medium 통일 후 전체 LIVE 회귀는 미실시 |

현재 채택한 HTTP·웹 UI·SQLite와 향후 후보인 Chroma·임베딩·MCP를 구분한다. 실행 코드는 prototype/에 있다. Hermes와 Docker는 필수가 아니다.

## 7. 기록과 신뢰성

- 신고, 문서 기재, API 조회, AI 추정을 서로 다른 출처로 표시한다.
- 첨부 접수만으로 자료 내용을 확정하지 않는다.
- 같은 인원 집계 범위에서 총원과 분류별 인원 합계를 검사한다.
- 상황·계획은 버전으로 보존하고 오래된 요원 결과가 최신 상황을 덮어쓰지 못하게 한다.
- 기상 예측값을 현장 관측값으로 표시하지 않는다. 기준시각·조회시각·좌표·단위를 보존한다.
- 자원표와 시연 사건은 가상 자료임을 표시한다.
- 권고안은 사람이 검토한다. 검증요원 통과는 안전·정확성 보증이 아니다.

## 8. 완료 기준

아래는 계획상의 목표이며 실제 완료 증거는 [04_개발계획.md](04_개발계획.md)에 기록한다.

1. 사용자가 채팅과 명부로 정보를 추가하고 상황실장이 실제로 재지시한다.
2. 지시·보고·도구 결과와 화살표가 같은 임무 ID에 연결된다.
3. 실제 기상 조회, 벡터 검색 근거, MCP 호출 증거를 제시한다.
4. 명부 불일치를 자동 확정하지 않고 확인 후 상황·계획을 갱신한다.
5. 검증 결과와 이전 대응안·변경 이유를 확인할 수 있다.
6. 도구 실패·이전 버전 보고를 처리하고 재실행 후 기록을 복원한다.
7. 모델 비교 결과와 실제 구현 범위를 발표에서 정확히 설명한다.
8. 세션 전환·검색·늦은 보고·재시작 후 기억이 섞이지 않는다.
9. 시뮬레이션 가정과 사실을 분리하고 사용 근거·조건·미확인사항을 포함한 조언을 제공한다.

공식 팀별 10분 표기를 기준으로 10분 구성과 5분 압축본을 준비한다. 명시된 프로젝트 수행시간 2시간의 달성 가능성은 사전 허용자료·교육 예제·연결 검증에 달려 있다.


## 9. 최신 운영 요구

상황실장은 지시를 짧게 이해하고 필요한 요원에게 먼저 맡긴다. 전문 분석과 필요한 정보 파악은 각 요원이 수행하고, 상황실장은 보고를 모아 질문의 이유와 핵심 제안을 전달한다. 첫 호출에서 모든 분석을 끝내는 구조는 개선 대상이다.

사용자는 짧은 정보를 여러 번 전달할 수 있어야 한다. 답변은 핵심 제안과 질문 1~2개를 우선하며, 전송 직후 상단 진행 상태와 단계 강조로 접수·배정·보고를 확인한다. 모델 설정은 내부 기록에 남기고 운영 화면에서는 숨긴다.

등록 세력은 사용자 제공 조직자료이며 출동 가능 상태의 실시간 증거가 아니다. 방제3호정은 사용자가 설명한 화재·충돌 등 오염 우려 시 즉시 출동 준비 원칙을 반영한다. 실제 출동은 담당자의 지시·확인 보고와 구분한다.
