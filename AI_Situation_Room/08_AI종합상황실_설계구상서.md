## 1. 의도

사용자가 상황실장과 대화하면서 사건을 해결해 나가고, 그 뒤에서 요원들이 조사·보고하며, 현재 상황과 대응계획이 하나의 기록으로 축적되는 AI 조직을 만든다.

대시보드는 결과 문장만 보여주는 화면이 아니다. 사용자와 상황실장의 대화, 요원에게 내려진 지시, 실제 조사와 보고, 변경 근거를 함께 보여준다. 해양사고는 첫 사례이고 제품과 역할 이름은 범용적으로 사용한다.

## 2. 구상이 발전한 과정

| 출발점 | 현재 방향 | 이유 |
|---|---|---|
| 신고 버튼 중심 | 지속 채팅·자료 첨부·질문·정정 | 사용자가 조사 과정에 참여 |
| 세 Agent 고정 호출 | 상황실장이 필요한 요원 선택 | 입력마다 필요한 일이 다름 |
| 선박정보요원 | 정보요원 | 다른 사건에도 적용할 역할명 |
| 상태 카드 | 실제 지시·보고 화살표와 상세 | 무엇을 주고받았는지 확인 |
| 답변 재생성 | 상황·계획 버전과 변경 이유 | 사건의 연속성 보존 |
| AI가 DB 관리 | AI 갱신안 + 프로그램 검사·저장 | 의미 해석과 정합성 분리 |
| 여러 외부 API | 무료 기상·해상 API만 | 최신 합의와 검증 결과 반영 |
| 방대한 사전 설계 | 진화적 프로토타이핑 | 짧은 시간 안에 실행 위험부터 해결 |

## 3. 상황실장과 프로그램의 경계

상황실장은 누구에게 무엇을 맡길지 판단하고 자연어 지시와 구조화 메타데이터를 만든다. 프로그램은 수신 요원·임무 ID·상황 버전·자료 참조를 검사하고 실행한다.

요원들은 상황실장에게 보고한다. 필요한 보고는 상황실장이 다른 요원에게 전달한다. 독립 작업은 병렬로 처리하지만 앞선 결과에 의존하면 기다린다. 새 정보·보고·사용자 요청이 없으면 대기한다.

보완 지시 1회, 제한된 재시도와 시간제한은 초기 구현 제안이다. 실측 이후 조정하되 무한 대화는 허용하지 않는다.

## 4. 기록 구조

상황판은 현재 알고 있는 것, 상황일지는 그렇게 알게 된 과정이다. 명부 7명과 최초 신고 5명은 둘 다 보존하고 출처가 다름을 표시한다. 최신 자료라고 자동으로 더 정확한 사실로 확정하지 않는다.

일반 DB는 사건·명부·대화·임무·기상·계획을 관리한다. 벡터DB는 지침에서 관련 근거를 찾는다. 첨부 원본은 별도 보존한다. AI가 직접 SQL을 만들거나 DB 스키마를 바꾸는 구조는 필요하지 않다.

## 6. 무료 기상과 RAG의 결합

정보요원은 사고 위치에 대한 기상 도구를 사용한다. 수색구조요원은 현재 상황에 해당하는 지침을 검색한다. 상황실장이 두 결과를 종합하되 기상자료의 종류·기준시각과 지침 출처를 잃지 않는다.

사용자 제공 동해 세력은 로컬 카탈로그로 제공하고 실시간 가용성과 구분한다. 가상 시나리오의 자산은 별도 신고 기록이다. 외부 데이터 API를 기상으로 제한하는 것과 모델 API·MCP를 사용하지 않는 것은 다르다. MCP는 기상 조회를 요원이 도구로 사용하는 실제 연결 경로로 계획한다.

## 7. 검증으로 바뀐 판단

AISStream은 두 국내 범위에서 각 30초 구독이 승인됐지만 선박 메시지는 없었다. 한국 전역이 영구 미지원이라고 증명된 것은 아니다.

공공 AIS API는 전체 1,719건과 번호 조건 검색을 확인했지만 수신일이 모두 2024년이며 위치 좌표가 없고 선박명 누락이 많았다. 현재 사고의 위치·기상을 자동 연결하는 목적에는 맞지 않는다.

따라서 선박정보·좌표는 사용자 제공으로 받고 기상 API를 우선한다. 이 결정은 데이터 검증 결과에 따른 범위 조정이며 이후 좋은 API가 확인되면 별도 검토할 수 있다.

## 8. 남은 결정

교육 플랫폼의 외부 연결과 검색·MCP 지원, 한국어 임베딩 모델, 기상 제공자 실제 응답, 모델 호출 비용·한도, 팀원 수, 발표시간·질의응답, 사전 준비물 허용 범위가 남아 있다.

현재 Python HTTP·SQLite·HTML/CSS/JavaScript를 채택했다. Open-Meteo 수동 경로는 구현, 응답 성공은 미검증이다. Chroma·MCP는 미구현이며 Streamlit은 초기 후보 기록이다. 채택 변경 시 관련 문서를 함께 갱신한다.
