# HAEON(해온) — 현재 상태와 인수인계

> 임시 프로젝트명: **HAEON(해온)** · 해양경찰 멀티에이전트 의사결정 지원 시스템. [명칭·소개 기준](docs/PROJECT_NAMING.md) (2026-09-27). ‘AI 오케스트라’는 협업 방식의 설명이며 이름에 포함하지 않는다.

> 최신 구현 검증: 2026-09-27 승인형 MCP 수신함 추가. Python 59개·공유 전송 JS·격리 Chrome DEMO 검증을 실행했다. 이전 시험 기록은 당시 조건으로 보존하며 이번 실제 핫스팟·팀 앱·LIVE 호출은 미실시다.
> 이 문서는 현재 구현 상태의 기준이다. 00은 문서 안내, 01·03·11·12는 제품 요구, 04는 개발 순서, 09는 개발 지침이다. 과거 시험 결과는 당시 조건 그대로 보존한다.

## 1. 제품과 개발 기조

사용자가 상황실장과 대화하면 필요한 전문요원이 업무를 나눠 검토하고, 상황실장이 개별 보고·확인할 정보·대응 제안을 모아 사용자에게 돌려주는 로컬 의사결정 지원 프로토타입이다. 해양사고가 첫 적용 사례다.

개발은 작은 흐름을 구현하고 실제 입력으로 검증하는 방식으로 진행한다. 발표의 목표는 업무 적용 가치와 교육성과를 실행 증거로 보여주는 것이다. 장식보다 실제 지시·보고, 정확한 정정, 근거, 짧고 읽기 쉬운 결과를 우선한다. 대형 상황실 모니터에 계속 켜두는 사용을 기본 요구로 둔다.

## 2. 최신 사용자 결정과 반영 상태

| 시뮬레이션 기반 조언 | 가정을 분리한 조건 비교와 요원·검증·종합 경로 | 검증된 물리 예측, 자동 과거 시뮬레이션 재사용은 미구현 |

### 상황실장의 역할

목표 흐름은 **접수 → 짧은 범위·우선순위 판단 → 전문요원 임무 배정 → 개별 보고·정보 요구 수신 → 검증 → 핵심 제안·질문 → 사용자 답변 반영**이다. 상황실장이 전문 분석을 먼저 완성해 요원에게 반복시키지 않는다.

정보요원은 신고·명부·누락 정보, 수색구조요원은 대응지침·위험, 자원지원요원은 세력 후보·제약, 검증요원은 근거·모순·가정을 맡는다. 사용자에게는 공개 가능한 배정 이유, 수행 상태, 근거와 보고 요약을 보여준다. ‘전체 생각을 읽는다’는 요구는 이 협업 흐름의 가시성을 뜻하며 내부 추론 원문을 표시하지 않는다.

현재 코드에는 단순 신고·이름 정정을 상황실장이 직접 장부에 반영하는 최적화가 남아 있다. 이 방식은 이전 청해호 시험에서 호출을 줄였지만, 이후 사용자가 강조한 빠른 배정 요구를 완전히 구현한 것은 아니다. 초기 해석과 전문 추출·검토의 책임 분리를 다음 개발에서 다룬다.

## 3. 실제 아키텍처와 기술스택

| 영역 | 현재 구현 |
|---|---|
| 화면 | 별도 프레임워크 없는 HTML·CSS·JavaScript, `prototype/static/` |
| HTTP | Python 3 표준 라이브러리 `ThreadingHTTPServer`, `127.0.0.1:8860` |
| 저장 | SQLite `sessions`, `objects`, `settings`; 세션 장부와 JSON 기록 |
| 작업 | 세션 작업자 4개, 요원 작업자 6개, 전체 모델 호출 슬롯 6개 |
| 순서 | 같은 세션 요청은 순차, 서로 다른 세션과 독립 요원은 병렬 |
| 모델 | 서버에서 Responses API 호출, `gpt-6-luna`, 모든 역할 `medium` |
| 검색 | TXT/MD 단어 일치·CSV 요약 기반 첨부 최대 5개 선별, 공통 매뉴얼·세력 목록 첨부 |
| 기상 | Open-Meteo Forecast 수동 조회 함수; 실제 응답 성공은 별도 검증 필요 |
| 화면 동기화 | 약 1초마다 저장 상태 조회. 조회만으로 모델·기상 호출하지 않음 |
| 실행 파일 | macOS `상황실 실행.command`; Python과 `certifi`, 로컬 키 파일 필요 |
| 발표 | `presentation/index.html` 별도 HTML 설명 자료. 앱과 다른 산출물 |

Streamlit은 초기 후보였으며 현재 앱에는 쓰지 않는다. Chroma·임베딩·벡터 RAG·해상 파고·자동 기상 스케줄은 아직 구현하지 않았다.

```text
담당자 / → POST 접수 → 원문·run 저장 → 세션별 대기열
  → 상황실장 plan (현재: 해석 + 갱신안 + 배정)
  → 규칙 출동 후보 결합 → 버전·인원 검사와 갱신
      ├─ tasks 없음: 저장 결과·확인 질문을 사용자에게 반환
      └─ tasks 있음: 선택 전문요원 병렬 → 검증요원 → 상황실장 최종 보고
  → SQLite 저장 → 담당자 화면과 고정 /monitor가 같은 상태 조회
```

현재 `plan`의 결과 전체가 도착해야 전문요원 호출이 시작된다. 화면의 빠른 접수 효과가 이 API 대기를 없애지는 않는다. 매뉴얼 후보도 `Engine.process()`에서 요원 실행 전에 생성·기록되고 최종 보고에 합쳐진다. ‘요원 먼저 분석, 상황실장 나중 종합’이라는 최신 방향에 맞춰 이 순서를 바꿀 필요가 있다.

## 4. 기억·정정·근거·모델 설정

- 세션별로 대화, 현재 인원·위치, 선박 장부, 이름·직책, 환자 그룹, 세력 상태, 첨부, 실행, 보고, 호출 기록을 저장한다.
- 명부는 안정적인 인물 ID에 필드를 병합한다. 이름 오기 정정은 이름 필드를 바꾸고 직책·위치·건강 상태·구명조끼 정보를 보존한다.
- 위치별 분포는 현재 전체 분포로 교체한다. 지원선 자체 인원은 사고선박 대상자 총원에 더하지 않는다. 구조 후 재이송은 구조 누계를 증가시키지 않는다.
- 사용자 신고는 독립 실측과 구별한다. ‘의심’, ‘예정’, ‘관찰되지 않음’을 확정 사실로 바꾸지 않는다. 원문과 정정 전 상태를 보존한다.
- 시뮬레이션은 `run.kind=simulation`, `assumptions`, `based_on_version`으로 저장하며 실제 장부를 바꾸지 않는다. 별도 Simulation·Advice·MemorySummary 테이블은 없다.
- LIVE 계획 호출은 최근 대화 4건과 현재 장부 등을 사용한다. 전문요원은 과거 대화 전체 대신 현재 장부·최신 신고·공통 근거를 받는다. 전문요원별로 자료를 세밀하게 다르게 고르는 구현은 아직 부족하다.
- 긴 기억의 자동 요약은 없다. 준비한 컨텍스트가 현재 제한을 넘으면 오류를 반환하고 기존 기록을 보존한다.
- 모델 호출 설정은 `prototype/models.py`, 실제 요청·응답 ID·사용량·시간은 세션의 `calls`에 기록한다. 화면에서 모델명을 숨기는 것과 호출 기록 보존은 별개다.
- 키가 있는 새 세션은 LIVE 기본 선택이다. 기존 DEMO 세션은 자동 변경하지 않는다. API 실패를 데모 성공으로 대체하지 않는다. 직접 API의 세션 생성에서 mode 생략 시 기본값은 아직 demo다.

## 5. 기본 매뉴얼과 가용세력

공통 자료는 `prototype/manuals/basic-response-manual.md`와 `donghae_assets.json`이다. `tools.evidence_for()`가 `basic_manual`, `donghae_assets` 근거로 매 호출 문맥에 넣는다. 단순 화면 소개용 자료가 아니다.

| 사용자 제공 분류 | 등록 세력 | 사용자 제공 운용 범위 |
|---|---|---|
| 대형 | 3007함, 3016함, 3017함, 3018함, 5001함 | 주로 광역·울릉도 인근, 정박 중일 수 있음 |
| 중형 | 306함 | 연안부터 근해 |
| 소형 | 205정, P-60, P-65, P-72, P-97정 | 주로 연안 경비 |
| 특수 | 형사기동정, 예인3호정, 방제3호정 | 역할별 사건 지원 |
| 방제3호정 운용 설명 | 화재·충돌 등 해양오염 우려 시 바로 출동 가능하게 준비 | 현재 위치·가동 상태를 확인한 뒤 지시안에 사용 |

별도로 현재 카탈로그에는 묵호·동해·삼척·임원 파출소 연안구조정 후보 4개가 들어 있다. 이 목록은 사용자가 직접 준 함정 목록과 구분하며, 공식 편제·관할·현 위치의 최신 확인을 완료했다고 주장하지 않는다. 청해호 시나리오의 **301함**은 가상 신고 속 출동 자산이다. 사용자 제공 카탈로그의 **306함**과 혼동하거나 자동 치환하지 않는다.

기본 매뉴얼은 공개 소개·사례·훈련자료와 사용자 운용 설명을 정리한 앱용 보조 자료다. 승인된 기관 SOP 원본이 아니다. 기존 문서의 출처 URL은 보존했으며 이번 현행화에서 공개 사이트를 다시 검증하지 않았다.

현재 추천은 위험 키워드와 위치 문구에 따른 규칙 후보를 모델 제안과 합치는 방식이다. 실제 거리·ETA·가동 여부로 최적 세력을 고르지 않으며 실제 명령 전송도 없다. ‘기름 유출 없음’, 진압 완료, 지원 종료처럼 위험을 부정하거나 해소한 문구에도 키워드가 남아 후보가 반복될 수 있다. 규칙 후보가 먼저 오므로 화면의 앞 2개가 검증된 최우선 2개라는 보장은 없다.

## 6. 화면과 사용법

담당자 화면 `/`에는 세션 목록·채팅·상황실장·요원·검증·최종 보고·현재 상황·근거·실행 이력이 있다. `/monitor`는 고정한 세션을 읽으며 채팅 입력 영역을 숨긴다. 담당자가 다른 세션으로 이동해도 고정 세션은 유지된다. 별도 인증된 읽기 전용 권한 계정은 아니다.

- 입력창에서 Enter로 전송, Shift+Enter로 줄바꿈한다.
- 전송 즉시 접수와 진행 효과를 보여준다. 서버 저장 상태가 도착하면 배정·요원 검토·보고·최종 종합으로 갱신한다. 꾸며낸 생각이나 완료율을 표시하지 않는다.
- 제안과 질문은 각각 최대 2건을 기본 표시한다. 둘을 합쳐 최대 2건인 것은 아니며, 전체 생성 분량을 줄인 것도 아니다.
- 질문에는 이유를, 요원의 요청에는 출처를 표시한다. 상세 근거·미확인사항·원문은 별도 창에서 확인한다.
- ‘상황판에 고정’ 후 ‘대형 화면 ↗’을 연다. 복귀는 ‘상황실로 돌아가기 ↩’, 브라우저 전체화면은 전체화면 버튼 또는 Esc를 사용한다.
- 목록의 ×를 누르면 삭제 확인이 나온다. 대기·진행 작업이 있으면 삭제가 거절된다. 삭제는 해당 세션의 DB 기록과 고정 설정을 지우며 외부 백업·내보낸 파일은 삭제하지 않는다.
- 수신 지연 10초 초과와 연결 끊김 30초 초과를 구별한다. 모델 응답 대기와 서버 연결 이상은 다르다.
- 상세 창은 연 시점의 자료다. 새 장부를 보려면 닫고 다시 연다. 초안은 현재 브라우저 메모리에서 유지되며 새로고침까지 영속 보장하지 않는다.

삭제 버튼·복귀 링크·모델 표기 제거는 코드와 단위 수준 검증까지 마쳤다. 최신 브라우저 전체 동선·원거리 가독성·2시간 내구성 시험은 별도로 남아 있다. 앱의 ‘구현 범위’ 안내에는 세션 삭제가 미구현이라는 오래된 문구가 아직 남아 있어 다음 화면 수정 때 정리해야 한다.

## 7. 실행과 키 입력

1. Finder에서 프로젝트 폴더를 연다. 숨김 폴더는 `Command+Shift+.`로 표시한다.
2. `prototype/.secrets/openai_api_key.txt`에 키 한 줄을 직접 넣는다. `.txt`가 맞으며 파일명은 `.txt.txt`가 되지 않게 한다. 문서·소스·대화에 키 값을 쓰지 않는다.
3. 프로젝트 루트 `상황실 실행.command`를 더블클릭한다. Python 3와 `certifi`가 필요하며 없으면 실행 파일의 안내를 따른다.
4. 터미널을 열어두고 `http://127.0.0.1:8860/`에서 사용한다. 종료는 서버 터미널의 Control+C다.
5. 코드·모델 설정·삭제 API 변경 적용은 서버 종료 → 실행 파일 재실행 → 브라우저 새로고침 순서다. 실행 파일은 서버가 이미 열려 있으면 브라우저만 열기 때문에 자동 업데이트·재시작되지 않는다.

직접 `python3 -m prototype.server --port 8860`으로 실행할 때는 `OPENAI_API_KEY` 등 실행 환경을 별도로 설정해야 한다. 서버 자체는 비밀 파일을 자동으로 읽지 않는다. 기록은 `prototype/runtime/room.sqlite`에 저장한다. 백업은 서버 종료 후 runtime 폴더를 복사한다. 비밀 파일과 runtime은 발표 배포물에 넣지 않는다.

## 9. 발표·시상 전략과 작성 근거

HTML 발표자료는 방향키·휠·전체화면과 입체 전환으로 제품 흐름을 설명한다. `B`는 작성 근거, `N`은 발표 노트다. 이전 장면 요소가 남는 문제를 수정한 이력은 있지만 이번 문서 작업에서 전환을 다시 실기 검증하지 않았다. 현재 자료는 A호 5→7명 예시를 사용하는 설명 자료이며 최신 앱의 모든 기능·LIVE 결과를 자동 반영하지 않는다.

필수 설명은 **필요한 시점에 필요한 전문 역할만 선택해 검토 범위를 좁히고, 독립 업무를 병렬 처리하며, 상황실장이 근거와 보고를 종합한다**는 것이다. 역할별 전문성은 현재 역할 지침·제공 근거에서 온다. 별도 전문가 모델 학습을 완료한 것은 아니다. 모든 요원이 받는 근거를 역할별로 더 줄이는 작업도 남아 있다.

시상 전략은 공식 교육 내용인 Agent·RAG·MCP·모델 비교·신뢰성을 하나의 업무 사례와 실제 증거로 연결하는 것이다. 세부 배점과 수상 가능성은 확인되지 않았다. 현재 Agent·저장·정정·병렬 실행 증거는 있고 MCP 승인형 수신 증거는 2026-09-27 추가했다. 벡터 RAG·멀티모델 비교는 없다. 일반 함수나 단어 검색을 이 교육요소의 완료 증거로 바꾸지 않는다.

자료의 근거는 사용자 요구와 사건 원문, 00~12의 제품 설계, 제공 커리큘럼에 대한 기존 기록, 공개 자료 출처가 있는 기본 매뉴얼, 소스 코드, 날짜별 시험 보고서다. 외부 자료의 최신성·공식 일정은 이번에 새로 검증하지 않았다. 시간·토큰 비교는 한 사례의 참고 수치이며 단일 AI보다 비용·속도·정확도가 우수하다는 증거는 아니다.

## 11. 기능별 상세 구현 문서와 향후 연동 — 2026-09-27

다른 AI가 구현할 수 있도록 [상세 구현 안내](docs/implementation/README.md) 아래에 15개 기능·공통 계약 문서를 추가했다. 데이터 필드·요청/응답 예제·상태 전이·병합 규칙·오류 처리·코드 위치·수용 사례를 기록했다. 구현할 기능과 공통 데이터(02), HTTP(13), 검증(15)을 함께 읽는다. 기존 제품·개발 문서는 요구·방향·이력을 유지한다.

이번 코드 대조에서 다음 주의점도 상세 문서에 명시했다.

- 신고 update는 부분 병합, distribution은 전체 교체, 수동 facts는 remaining 예외가 있는 전체 교체다.
- 장부 반영 후 요원이 실패해도 이미 저장한 장부를 전체 실행과 함께 롤백하지 않는다.

- simulation에 질문만 있는 직접 반영 경로가 선택되면 실제 비교 보고를 보장하지 않는다. 가정은 run/원문에 남지만 직접 receipt의 assumptions는 비어 있다.

이번 작업은 문서 추가·연결이다. 문서의 링크·JSON 예제·코드 계약을 검사하며, 단위·HTTP·브라우저·새 LIVE·외부 기상 호출은 실행하지 않는다. 실제 검사 결과는 PROGRESS의 2026-09-27 항목에 기록한다.

Link-One·RESAID AI용 `submit_field_report`를 별도 인증 MCP 포트에서 제공한다. 수신은 원문/이력 저장과 알림만 수행한다. 담당자가 인용하여 전송하면 기존 채팅·상황실장·요원 흐름에 들어간다. 작성 중 초안은 보존한다. 사건 매핑·중복 수신/승인·거절/나중에 처리·삭제 사건 재전송 방지·재시작 이력 보존을 구현했다. 인용 및 외부 근거 기반 후속 요약은 출처를 유지하며 장부 자동 반영을 막는다.

기존 기능별 18개 문서를 현재 소스와 대조하고 19 화면 재구현, 20 모듈 인터페이스, 21 계약 예제, 22 미구현 개선, 23 현재 프롬프트를 추가했다. [재구현 전달 안내](docs/handoff/README.md)와 [단계별 계획](docs/handoff/REBUILD_PLAN.md)에 현재 복원 작업 1~9와 최신 요구 개선 작업 10을 구분했다. 통합 명세는 매뉴얼·18개 세력 카탈로그·청해호 15건까지 포함하며 앱 소스 없이 전달하는 문서다. 키·runtime·실제 사용자 세션은 제외한다.

소스 대조로 MCP 미구현이라는 오래된 현행 안내와 Python 시험 42개 설명을 수정했다. 현재 정의는 핵심 39+inbox 12+HTTP/MCP 8=59개다. 오늘 59개를 실행했다는 뜻은 아니다. UI에는 과거 브랜드·DEMO 접수 LIVE 문구·세션 삭제 미구현 안내가 남아 있고, progressState가 assigned와 critic을 병렬 실행처럼 묶을 수 있다. 이런 표현 차이는 19·22에 기록했으며 앱 기능은 수정하지 않았다.

[폴더 구조 검토](docs/FOLDER_GUIDE.md)에 편집 원본·배포본·역사 자료를 구분했다. 루트 README와 docs/README, handoff 폴더를 추가했으며 기존 파일·실행 경로·사용자 자료를 이동/삭제하지 않았다. 로컬은 해온 프로젝트이며 GitHub의 다른 두 프로젝트/권한/원격 상태는 이번에 조사하지 않았다.

다른 AI 플랫폼의 실제 문서 전용 재구현·픽셀 동일성·새 LIVE·실제 팀 앱/핫스팟 검증은 미실시다. 새 코드로 재구현한 플랫폼은 단계별 시험 결과로 동등성을 확인해야 한다.

### 2026-09-28 문서 검증 결과

- 명세·진입 안내의 로컬 링크 157건, JSON 예제 20개를 검사했다. 통합본 30개 절과 내부 링크 116건의 대상이 존재한다.
- 전달 ZIP은 통합 명세·안내·manifest 3개 파일만 포함한다. 포함 문서와 대조 코드 해시를 확인했다. 앱 소스·키·토큰·runtime 본문은 포함하지 않았다.
- 임시 DB와 DEMO provider로 문서 계약 예제 4그룹을 확인했다: A(4 calls/2 tasks/2 messages와 중복 재실행 없음), B(이름만 정정·전체 분포 교체·합계 오류 거절), D(가정과 facts/version 분리), E(수신만으로 무실행·승인 검토 후 사실 유지·중복 접수/승인 방지). 이는 문서 예제의 국소 계약 검사이며 전체 단위 59개를 실행한 것이 아니다.
- 이번 앱 전체 단위/HTTP/브라우저/LIVE·기상 외부 호출·다른 AI 플랫폼 재구현·GitHub 원격 업로드는 미실시다. 앱 코드와 기존 사용자 자료는 수정하지 않았다.

## 2026-09-28 · 기상 API 검토와 저장소 동기화

사고해점 풍향·풍속·파고·시정·날씨의 무료 API 후보를 [기상 연동 개선사항](docs/improvements/02-incident-weather.md)에 기록했다. 현장 보고를 우선 표시하고 주변 관측·모델 예보·시각/출처를 구분하는 방향이다. 기존 기상 조회 코드는 이번에 변경하지 않았다. HAEON 명칭·발표 개정·재구현 명세 및 이 검토 내용을 기존 GitHub AI_Situation_Room 경로로 동기화한다. 비밀·실행 DB는 제외하고 다른 두 프로젝트는 보존한다.
