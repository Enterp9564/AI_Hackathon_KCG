## 1. 시간과 선행 조건

커리큘럼의 프로젝트 수행은 9/30 15:00부터 17:00까지 2시간이다. 10/1 09:30부터 12:00은 발표 준비·제출이므로 개발시간으로 자동 합산하지 않는다. 코드 수정 허용 범위와 사전자료 재사용 조건은 현장에서 확인한다.

전체 목표를 2시간 안에 달성하려면 교육 예제, 실행 환경, 자료, API 접근, 임베딩 다운로드가 준비돼야 한다. 준비 없이 전체 범위 완성을 보장하지 않는다. 남은 기능이 있으면 구현 상태를 공개하고 발표 표현을 맞춘다.

## 4. 120분 운영안

아래는 선행 검증과 허용된 예제 활용을 전제로 한 목표 배분이다. P0부터 P7의 실제 난도에 따라 조정한다.

| 경과시간 | 목표 |
|---|---|
| 0분부터 10분 | 준비 상태 확인, 미확인 연결 위험 선별 |
| 10분부터 30분 | P0·P1: 저장되는 채팅과 실제 지시·보고·재지시 |
| 30분부터 50분 | P2·P3: 기상 조회와 명부 정정 |
| 50분부터 75분 | P4·P5: 문서 근거·자원·MCP·검증 연결 |
| 75분부터 95분 | P6·P7: 흐름 통합, 모델 비교 기록, 화면 정리 |
| 95분부터 120분 | 신규 기능 중단, 핵심 검증·녹화·백업 |

모델 비교용 입력·정답, 발표 화면 캡처, 한 문장 설명은 개발 중 계속 준비한다. 60분까지 작은 전체 흐름이 없으면 장식·도면·파일 형식 확장부터 줄인다. 기상·벡터 검색·MCP를 몰래 가상 처리해 완료했다고 하지 않는다.

최신 확장 계약은 [12_모델배정_시뮬레이션조언_세션기억.md](12_모델배정_시뮬레이션조언_세션기억.md) §5를 따른다. 모든 세션 소유 객체의 session_id를 저장·조회·검색·결과 반영에서 검사한다. Simulation·Advice·MemorySummary도 같은 경계를 사용한다.

run_id는 사용자 요청 한 건의 실행 묶음이며 원본 message_id와 연결한다. 배정 요약·이유, 개별 보고 수신, 종합·검증, 최종 메시지의 사용 보고 ID를 저장해 요청에서 최종 답변까지 추적한다.

claims는 값·출처·확인 상태를 묶는다. 자유문 보고와 구조화 필드를 함께 사용한다. DB 테이블 수를 위 객체 수에 맞춰 억지로 늘릴 필요는 없다.

요원 보고의 모든 근거 ID는 실제 자료나 도구 결과에 존재해야 한다. 화면에서 필요한 요약을 별도로 두되 근거 원문을 잃지 않는다.

## 7. 상황 갱신과 동시 실행

1. 새 입력을 원본 메시지로 먼저 저장하고 접수 이벤트를 만든다.
2. 상황실장이 갱신안과 필요한 임무를 만든다.
3. 프로그램이 버전·역할·필수 값·인원 관계를 검사한다.
4. DB 거래 안에서 예상 버전과 현재 버전이 같을 때만 새 상황 버전을 저장한다.
5. 준비된 독립 임무를 동시 실행 슬롯에 함께 전달한다. 첫 응답을 기다린 뒤 다음 독립 임무를 시작하지 않는다. 선행 근거가 필요한 임무는 depends_on 완료 후 실행하며 동시 호출 한도 대기를 구분한다.
6. 작업 중 새 입력은 사건별 대기열에 넣는다.
7. 오래된 버전의 보고는 보존하되 최신 계획에 자동 병합하지 않는다.
8. 각 보고는 도착 즉시 저장·표시하고 상황실장 수신 현황을 갱신한다. 필요한 보고가 준비되면 종합·검증하며 수정 필요 시 제한된 보완 지시를 실행한다.
9. 사용 보고·누락 근거·상황 버전에 연결된 최종 답변을 저장하고 사용자 채팅과 상황판에 같은 메시지로 전달한다. 실패·판단 보류를 정상 완료로 바꾸지 않는다.

초기 설정 제안: 보완 지시 최대 1회, 호출 시간제한, 일시적 네트워크 오류 재시도 최대 1회. 실제 처리시간과 호출 한도로 조정한다. 타임아웃·버전 충돌을 실패 상태로 남긴다.

## 8. 데이터·도구 구현 경계

- 명부: CSV 전체 읽기, ID 중복·누락 검사. 벡터 top-k로 총원 산정 금지.
- 지침: 3개부터 시작, 절·문단 단위 분할, 문서명·절·원문·버전 메타데이터.
- 검색: 관련 구절 3개 정도를 반환하고 질문 5개로 한국어 품질 확인. 고정 검색 결과 금지.
- 기상: 정보요원에 get_weather 도구 1개 노출. 내부에서는 일반기상·해양 API를 각각 호출할 수 있다.
- MCP: 클라이언트 → MCP 도구 → 기상 함수 → 외부 API 경로를 실제로 확인한다.
- 자원: 사용자 제공 동해 세력의 로컬 JSON으로 한정. 실시간 자원 조회라고 표시하지 않는다.
- 캐시: 위치·시각·요청 항목을 키로 사용하고 자료 나이와 캐시 여부를 표시한다.
- 모델 비교: 같은 입력·근거·평가 기준으로 2개 모델을 비교한다. 교육 계정 접근이 없으면 미실시로 기록한다.

| 모니터링 UI·UX 문서 | 설계안 작성 | 11번 문서 |
| 지시·병렬 실행·보고 흐름 | 데모 실행·시간 중첩 검증 | 요청·임무·보고·최종 메시지 연결, 실행 시간 중첩, 의존 대기 |
| 공통 스냅샷·두 화면 | 구현·세션 전환과 상황판 고정 확인 | 입력 유지, 버전 일치, 중복 호출 없음 |
| 연결·신선도·알림·복구 | 일부 구현: 지연 표시·이전 버전·중단 복구; 전체 수용 기준 미완료 | 11 §16의 실패·복원 사례 |
| 대형 화면·장시간 사용 | 미검증 | 실제 장비·거리·연속 시험 결과 |

표시 주기와 외부 도구 조회 주기는 분리한다. 상태를 읽을 때마다 AI·기상 요청을 실행하지 않는다. 필요한 질문·알림·연결 정보는 기존 Event와 구조화 필드로 작게 추가하고, 새 프레임워크 도입부터 시작하지 않는다.

## 12. 모델·조언·여러 세션 확장 — 2026-09-25

12번 설계 문서를 구현 기준에 추가한다. 상황실장과 나머지 네 요원 모두 GPT-6 Luna medium을 사용한다. 기존 단계의 첫 구현부터 session_id를 전달하고 P0에서 세션 생성·전환·복원을 확인한다. P1–P5의 요원·검색·보고에도 세션 격리를 적용한다. 시뮬레이션 조언은 근거·검증이 연결된 후 기준안과 대안 1개를 비교하는 작은 흐름으로 구현한다.

| 추가 항목 | 상태 | 완료 증거 |
|---|---|---|
| 역할별 설정 | 어댑터·과거 LIVE 확인, medium 통일 후 요청 형식 테스트 완료 | 최신 LIVE의 모델·effort 기록 재확인 |
| 여러 세션·독립 기억 | 구현·격리/복원/후속 기억 검증 | 교차 조회·늦은 보고 차단, 입력·복원 분리 |
| 시뮬레이션 기반 조언 | 가정 분리·비교 흐름 구현; 데모 규칙 기반, 실제 추론 미검증 | 가정·사실 분리, 비교 보고와 조언 근거 연결 |

추가 범위를 기존 120분 안에 모두 완료한다고 보장하지 않는다. 세션 소속은 나중에 덧붙이지 않고 최초 저장부터 적용한다. 구현·실증 여부를 발표 문구에 맞춘다.

## 13. 과거 기록: 첫 실행형 프로토타입 — 2026-09-25

`prototype/`에 Python 표준 라이브러리 HTTP 서버, SQLite, 서버 병렬 작업자와 HTML/CSS/JavaScript 화면을 구현했다. 별도 설치 없이 `python3 -m prototype.server --port 8860`으로 실행한다. 기존 발표 HTML은 유지한다.

[실행 안내](prototype/README.md) · [검증 증거 및 남은 범위](prototype/PROGRESS.md). 자동 테스트 22개 및 브라우저의 세션 생성·분리·고정 상황판·최종 보고·가정 비교를 확인했다. API 키가 없어 현재 작동 화면은 명시적인 데모다. Luna 실제 추론, 벡터DB/RAG, MCP와 장시간 운영 검증은 완료하지 않았다.

## 14. 과거 기록: 최초 LIVE 시나리오 수용 실패

사용자 키와 명시적 승인으로 청해호 가상 신고 15건을 순차 실행했다. 실제 gpt-6-luna 85회 호출이 완료됐고 상황실장 high·요원 medium 설정 및 병렬 작업을 확인했다. 다만 명부 이름 필드 정정, 채팅에서 현재 상황 데이터 자동 갱신, 신고 근거 연결은 실패/미지원이다. API 성공과 제품 수용 완료를 구분한다. [최초 시험 결과](prototype/scenarios/cheonghae-test-results.md)는 당시 실패 기록이다. 후속 개선은 §15와 13번 현행 문서를 따른다. 앞 절의 Luna 호출 미검증·키 없음 표시는 이 시험으로 갱신된다.

## 15. 신고 자동 갱신·명부 정정 개선

사용자 승인으로 신고 장부·위치별 인원·환자 그룹·명부 필드 정정과 원문 근거를 구현했다. 실제 청해호 최종 상태 검사와 회귀 테스트 36개가 통과했다. 단순 갱신 8건은 요원 추가 호출 없이 처리했다. 중간 위치 합계 불일치 1건은 잘못된 저장을 차단하고 전체 분포 교체로 수정·재검증했다. [최신 결과·비교 수치·남은 한계](prototype/scenarios/cheonghae-improvement-results.md). 이전 절의 해당 기능 미구현 상태를 갱신한다.


## 16. 현재 완료 범위와 다음 작업 — 2026-09-26

현재 UI와 실행 코드는 Python HTTP·SQLite·HTML/CSS/JavaScript다. 매뉴얼·사용자 제공 동해 세력·구조화 정보요구·핵심 2건 접기·상단 진행·글로우·Enter 전송·전 역할 medium·모델 표기 제거·세션 삭제·대형화면 복귀를 반영했다.

핵심 단위 39개, JS 문법, 기존 청해호 v3 저장 결과 검사 PASS를 이번에 확인했다. HTTP 3개·새 LIVE 호출·최신 브라우저 동선은 실행하지 않았다. 이전 절의 22/36개 등 수치는 각 당시 기록이다.

다음 순서는 초기 배정과 전문 검토 분리 → 현재 상황에 맞는 질문·출동안 1~2개 선정 → 최신 동선과 medium LIVE 회귀 → RAG·MCP·모델 비교·발표 증거다. 세부 차이와 검증 기준은 [13번 §10](13_현재상태_요구사항_인수인계.md#10-다음-개발-순서)을 따른다. 자동 보완 루프·재시도·기상 스케줄은 위 설계 제안이며 현재 구현이 아니다.
